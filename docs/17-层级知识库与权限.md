# 层级知识库与权限

## 知识库结构

知识库是空间内的树形标签。节点通过 `parent_id` 形成层级，文献通过 `asset_tag` 与一个或多个节点关联；同一份 PDF、解析结果、语义分片和向量只保存一份。早期未带空间的租户级标签继续兼容读取，新建知识库带 `space_id`。

知识库节点的选择包含该节点的全部后代节点。选择“肿瘤”时包含“胶质瘤”等子知识库；选择“胶质瘤”时不包含兄弟节点或只直接归属于“肿瘤”的文献。资产列表接口和语义检索接口都按此规则展开标签筛选。

文件夹是资产的物理整理结构；知识库树是逻辑分类、权限和检索范围，两者相互独立。

## 知识库权限

知识库成员记录在 `tag_member`，角色使用 `owner`、`editor`、`viewer`。成员对节点的权限向下继承到全部子节点，不向上或横向继承：父节点成员可以访问整个子树，子节点成员不能访问父节点的其他子树。

用户只有在文献至少关联一个其有权限的知识库节点时，才可以看到文献、检索到文献、查看 PDF 原文、查看解析结果、查看语义分片、使用媒体预览或获得引用。空间权限仍作为底层租户边界；空间 owner/editor 可以管理空间内未分类资产，普通 viewer 受知识库权限过滤。

未分类文献不对普通 viewer 开放，便于导入和自动分类流程先完成处理再分配知识库。

## 管线自动归类

管线在解析和向量化完成后执行自动归类（`services/worker/src/loomvec/worker/tasks.py` 的 `_auto_assign_knowledge_bases`），语料为文献名、PDF 元数据（标题/主题/作者）和解析出的 Markdown 前 24000 字：

1. **从现有知识库选择**：有可用 LLM 时，把当前空间的知识库目录（含早期租户级标签和 `pending` 节点，每行 `id\t名称`）连同语料交给 LLM，只采纳目录内的 id 且置信度至少 0.75 的节点。
2. **没有合适节点时建议新建**：仅当 `config/loomvec.json` 的 `pipeline.auto_create_knowledge_bases` 为 `true`（默认）且当前空间未删除的 `pending` 节点少于 `pipeline.max_pending_knowledge_bases`（默认 20）时，提示词才向 LLM 索要新知识库建议；否则 LLM 只从目录中选择。提示词要求优先复用现有节点（包括较宽泛的上级节点），只有目录中没有任何节点能覆盖文献核心主题时，才在返回的 `new_knowledge_base` 中给出一个新知识库（名称、可选的上级节点 id、置信度、一句话理由）。空间还没有任何知识库时同样走这一步（允许新建时）。建议置信度至少 0.75 才处理；上级 id 不在目录内时新节点挂在根下。每篇文献最多建议一个。
3. **新建前查重**：经 `services/core/src/loomvec/core/knowledge_base_auto.py` 的 `create_system_tag`（系统路径，不做人工权限校验）落库，依次判定：
   - **同名复用**：名称先做 NFKC 归一（折叠全角、上标等书写变体）、折叠空白，再取查重键（casefold、英文单词词尾单个 `s` 去掉、去掉空白/标点/下划线；两侧都是字母数字时连字符按分隔符去掉，否则保留），与空间内全部未删除节点（含 `pending` 和早期租户级标签）的查重键**完全相等**才视为同名，直接复用已有节点（`active` 优先）。只认同一名称的不同写法（如「Graph Neural Networks」与「graph-neural-network」、「LLMs」与「LLM」）；不做相似度模糊匹配，「1型糖尿病」与「2型糖尿病」、「HER2阴性乳腺癌」与「HER2阳性乳腺癌」、「神经网络」与「图神经网络」这类近似名称，以及「HER2+」与「HER2-」（含上标 ⁺/⁻、全角 ＋/－、「HER2(-)」、「CD4^{-}」等写法变体）这类正负号后缀各自是不同节点；规范化后不含任何字母数字的纯符号名称（如「---」）一律视为空名称。
   - **合并重定向**：查重键相同的节点曾被人工合并掉（`tag.merged_into` 非空）时，沿合并链返回仍存在的合并目标，不新建。
   - **删除即否决**：查重键相同的节点曾被删除（未合并）时，视为人工已否决，不再建议、不新建。
   - **数量上限**：空间未删除的 `pending` 节点已达 `pipeline.max_pending_knowledge_bases` 时不新建（同名复用和合并重定向不受限）。
   - 名称超过 64 字符时拒绝。新节点 `status=pending`、没有创建人和成员；LLM 给出的理由只记在 worker 日志事件 `knowledge_base_auto_created` 中，不落库。
   - **并发**：同一空间的系统新建在事务级 advisory lock（`pg_advisory_xact_lock`）内完成查重、计数与插入，覆盖空间租户为空时唯一约束 `uq_tag_space_name` 不生效、以及同名不同写法并发新建的情况；人工同时建了完全同名的节点时由唯一约束兜底，复用那一行。
4. **兜底**：LLM 不可用或没有有效结果时，按语料中是否出现节点名称做确定性匹配，只匹配现有节点，不新建。
5. **写入前复核**：写文献关联前对全部候选节点按 id 升序一次性加 `FOR KEY SHARE` 行锁（持有到提交）并复核：已被合并的改挂到合并目标，已删除的跳过。人工合并对源/目标按 id 升序加 `FOR UPDATE`，两者按同一全局顺序加锁、互斥，自动关联不会挂到并发合并掉的节点上，也不会和合并各自逐个加锁顺序不一致而死锁；合并改挂子节点只是普通 `UPDATE parent_id`，不与 `FOR KEY SHARE` 冲突。

自动关联记录来源为 `auto`，人工关联记录来源为 `manual`；编辑文献的人工标签时保留自动关联；归类失败不会回滚已经完成的处理结果。

## 待确认知识库（pending）

`tag.status` 取值 `active`（正式节点；人工创建的节点和存量节点都是 `active`）或 `pending`（管线自动新建、待人工处理）。存量库由 `make init-db`（`loomvec.api.init_db` 的增量补列）加上 `status` 与 `merged_into` 两列，已有行补为 `active`。`pending` 节点和正式节点一样出现在知识库列表与树中、参与筛选和检索，由空间 owner 或该节点的知识库 owner（含从上级节点继承的 owner）处理：

- **确认**：改为 `active`。
- **合并**：只能合并 `pending` 节点；目标须是本空间（`space_id` 与当前空间相同）的其他未删除节点，不能是早期租户级标签，也不能是源节点自己的子节点；需同时具备源与目标两个节点的管理权限。源/目标按 id 顺序加 `FOR UPDATE` 行锁后复核状态，再把挂在源节点上的文献关联改挂到目标节点（文献已挂目标时去掉重复关联）、源节点的直接子节点改挂到目标节点下，最后记 `merged_into=目标` 并软删除源节点；源节点的成员授权不迁移。之后管线对同名建议与写入都会重定向到目标节点。
- **删除**：与普通节点相同，软删除节点及其子树；之后管线不会再自动建同名节点。

用户端知识库树当前不区分 `pending` 节点，也没有确认/合并入口；通过下列 API 操作。

## API

- `GET /api/v1/spaces/{space_id}/knowledge-bases`：返回当前用户可见的知识库节点平面列表，包含 `id`、`name`、`parent_id`、`status`（枚举 `active` / `pending`）、有效角色；前端据此组装树。可选查询参数 `status=active|pending` 只返回该状态的节点（可见性判定仍基于全部节点），如 `?status=pending` 列出待确认节点。
- `POST /api/v1/spaces/{space_id}/knowledge-bases`：创建根节点或子节点（人工创建的节点为 `active`）。
- `PATCH/DELETE /api/v1/spaces/{space_id}/knowledge-bases/{knowledge_base_id}`：修改层级或软删除节点及其子树。
- `POST /api/v1/spaces/{space_id}/knowledge-bases/{knowledge_base_id}/confirm`：确认节点为 `active`（已是 `active` 时原样返回）；返回节点。
- `POST /api/v1/spaces/{space_id}/knowledge-bases/{knowledge_base_id}/merge`：请求体 `{"target_id": "<目标节点 id>"}`，把 `pending` 节点并入目标节点；源节点不是 `pending` 时返回 409，目标为自身、其子节点或早期租户级标签时返回 422，源或目标已被删除（含加锁复核时发现被并发删除）时返回 404；返回目标节点。
- 确认与合并都需要 `write` scope，并由 `require_manager` 校验空间 owner 或知识库 owner 权限（租户级 API Key 身份不可操作）。
- `GET/PUT/DELETE /api/v1/spaces/{space_id}/knowledge-bases/{knowledge_base_id}/members`：读取、设置和移除知识库成员。
- `GET /api/v1/assets` 的 `tag_ids`：选择节点时自动包含全部后代节点。
- `POST /api/v1/search` 的 `tag_ids`：同样按子树展开，并在向量检索前按知识库权限收敛资产 ID。

## 用户端

空间资产页左侧显示知识库树，右侧显示当前知识库范围内的文件夹和文献。选择父节点默认包含子知识库；“全部知识库”显示当前空间内用户可见的全部文献。文献详情只显示用户有权访问的知识库标签。
