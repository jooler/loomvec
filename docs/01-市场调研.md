# LoomVec 前期调研：同类产品与实现方案

> 调研时间：2026-09 · 数据经 GitHub / 官方文档实时核对
> 注：本文为调研时点快照，最终决策以 [00-项目核心文档](./00-项目核心文档.md) 与 [03-解析分片与图谱检索](./03-解析分片与图谱检索.md) 为准——文档解析已定为 MinerU 内置自部署（License 合规项见 03），向量库已定为 Milvus，知识图谱已定为 PostgreSQL + Apache AGE，检索为三路混合召回+强制重排。

## 一、结论速览

1. **市场空白**：现有产品分两派——RAG/知识库问答平台（RAGFlow、Dify、FastGPT、MaxKB）和数字资产管理 DAM（ResourceSpace、Pimcore、Nuxeo）。**没有产品同时具备"传统资产管理体系（分类/标签/元数据/摘要）+ 真正的多模态语义检索（图片、视频可被语义命中）"**。现有 RAG 产品的"多模态"几乎都停留在对话层（把图片丢给 VLM 聊天），而非检索层的图文统一向量。
2. **可借鉴的成熟做法**：
   - 资产数据模型借鉴 DAM：资产主表 + 可定义元数据 schema（Pimcore）+ facet 能力组合（Nuxeo）+ 多版本 + 派生物（缩略图/转码产物）独立存储。
   - 语义索引借鉴 RAGFlow/Dify：chunk（语义单元）与原始文档通过 ID 关联，记录版面位置/页码实现"命中回溯原文"；RAGFlow 的 DeepDoc 甚至记录图片在页面中的坐标。
   - 视频/图片语义化是业界共识管线：**抽帧 → 图文嵌入 + VLM 生成 caption → caption 走文本嵌入通道**，转写与 caption 带时间戳，召回后可回溯到视频具体时间点。无生产级端到端视频嵌入模型。
3. **License 陷阱**：jina 系列（jina-clip-v2、jina-embeddings-v3/v4）为 CC-BY-NC，自部署禁商用；Marker 为 GPL-3；MinerU v3.1 起为附加条款许可（商用前需审阅）；FastGPT/Dify 有 SaaS 转售限制。可放心商用的：Qwen3 系列、BGE 系列、SigLIP 2、Docling、PaddleOCR、faster-whisper、PySceneDetect、libvips、Qdrant、Milvus、PostgreSQL。

## 二、开源知识库 / RAG 平台对比

| 产品 | 版本/Stars(2026-09) | 技术栈 | 存储 | 传统资源管理 | 多模态检索 | API/集成 | License |
|---|---|---|---|---|---|---|---|
| **RAGFlow** | v0.27.2 / 90.5k | Python+Go | MySQL + ES/Infinity + MinIO | 标签集+元数据（强） | 图片理解（非检索级） | REST+SDK+MCP | Apache-2.0 |
| **Dify** | 1.17.1 / 155.4k | Flask+Celery / Next.js | PG + 可插拔向量库 | 标签+元数据+父子分段 | 对话级 | BaaS 全 API | Apache2.0+附加条款 |
| **FastGPT** | v4.17.0 / 29.6k | Next.js/TS monorepo | Mongo + pgvector/Milvus | 标签+元数据过滤 | 弱 | OpenAPI | 禁 SaaS 转售 |
| **MaxKB** | v2.10.6 / 22.8k | Django+LangChain / Vue | PG + pgvector | 元数据 | 音视频对话级 | REST+网页嵌入 | GPLv3 |
| **AnythingLLM** | v1.16.1 / 65.9k | Node/Express / React | LanceDB 等 9 种 | 弱（Workspace） | 对话级 | Dev API+Widget | MIT |
| **Open WebUI** | v0.11.3 / 151.6k | FastAPI / Svelte | PG + Chroma 等 9 种 | 集合+标签 | 对话级 | OpenAI 兼容 API | 品牌条款许可 |
| **Onyx**（原 Danswer） | v4.7.1 / 32k | Python / Next.js | PG + Vespa | 元数据+**源系统 ACL 同步**（最强） | 对话级 | REST+50+连接器 | CE MIT |

**要点**：
- RAGFlow 的 DeepDoc（OCR + 版面识别 + 表格结构还原）是文档解析质量标杆，chunk 可视化并可人工修订；已支持 Docling/MinerU 作为可选解析后端。
- Dify 的"父子分段"（小块检索、大块送给生成）值得借鉴。
- Onyx 证明企业场景的核心痛点是**连接器与权限同步**（50+ 数据源连接器 + 文档 ACL 同步到检索层），这是"企业级"的关键标志。
- 上述所有产品的共性短板：**没有图片/视频作为一等公民的语义检索**；传统资产目录（分类树、元数据 schema、版本）管理弱。

## 三、多模态嵌入模型选型（可商用、可自部署、中文优先）

### 文本嵌入

| 模型 | 维度 | 上下文 | License | 评价 |
|---|---|---|---|---|
| **Qwen3-Embedding-0.6B/4B** | MRL 可裁剪 | 32K | Apache-2.0 | MTEB 多语言榜头部（8B=70.58），0.6B 已超 bge-large，中文强，**首选** |
| BGE-M3 | 1024 | 8K | MIT | dense+sparse+ColBERT 三模一体，长期中文标杆 |
| bge-large-zh | 1024 | 512 | MIT | 上一代，长文本弱 |
| jina-embeddings-v3/v4 | — | 8K | **CC-BY-NC** | 自部署禁商用，排除 |
| OpenAI / Cohere API | — | — | 商用 API | 闭源，数据出境与成本顾虑 |

### 图文统一嵌入

| 模型 | License | 评价 |
|---|---|---|
| **BGE-VL**（0.24B~1.5B） | MIT | 1 亿图文对训练，MMEB zero-shot SOTA，中文好，**首选** |
| SigLIP 2 | Apache-2.0 | 38 语，MMEB 超 CLIP，备选 |
| Chinese-CLIP | MIT | 仅图→文英文?（中文文本塔），成熟备选 |
| jina-clip-v2 | **CC-BY-NC** | 精度好但禁商用，排除 |
| Cohere embed v4 / voyage-multimodal-3 | 闭源 API | 精度顶级，云端方案备选 |

### 视频/音频：业界共识管线（无端到端生产级模型）

```
视频 → ffprobe 元数据
     → PySceneDetect 场景切分 → 每场景抽 1~3 代表帧
         → 帧走 BGE-VL 图文向量（可被"画面语义"命中）
         → Qwen2.5-VL(Apache-2.0) 对代表帧生成 dense caption → 走文本向量
     → 音频 → faster-whisper(MIT) 转写 → 带时间戳文本块 → 文本向量
所有语义单元记录 [start, end] 时间戳 → 命中后跳转原视频时间点
```

### 重排（Reranker）

Qwen3-Reranker-0.6B（Apache-2.0）或 bge-reranker-v2-m3（MIT），cross-encoder 精度优先。ColBERT/ColQwen 类 late-interaction 模型存储成本 10~100 倍，不作全库主通道，仅适合扫描件视觉检索增强，后续可选。

### 嵌入服务化

**Infinity**（单服务多模型：embed + rerank + CLIP，OpenAI 兼容 API）首选；TEI 性能最强但一容器一模型，多模型运维重；Xinference 适合多团队平台化；Ollama 不适合生产。**开发阶段可全部走云端 OpenAI 兼容 API（零 GPU），生产期再切自托管，经统一网关抽象仅需改配置。**

## 四、向量数据库对比

| 数据库 | License | 混合检索 | 多向量 | 元数据过滤 | 运维 |
|---|---|---|---|---|---|
| **Qdrant** | Apache-2.0 | sparse(BM25)+dense+Query API 融合 | 原生 multivector / named vectors | **最强**（filtered HNSW） | Rust 单二进制，最简 |
| **Milvus** 2.6+ | Apache-2.0 | 原生 BM25+dense，RRF | 多向量字段 + 3.0 EmbList | 强 | 亿~百亿级，组件多、偏重（有 Lite 版） |
| Weaviate | BSD-3 | BM25F 体验好 | named vectors | 强 | 中 |
| pgvector | PostgreSQL | 需 ParadeDB 补 BM25 | 不支持 | 中 | <1000 万向量够用，与业务库同栈 |
| ES/OpenSearch | AGPL/Apache | BM25 生态最成熟 | 不支持 | 极强 | 重 |

**选型结论（2026-09-11 已决策）**：初始版本即采用 **Milvus 2.6 Standalone**——原生 BM25+dense 混合检索、多向量字段、Partition Key 隔离，避免后期迁移成本；检索层仍封装接口用于评测对比。中文 BM25 用 Milvus 内置 BM25 Function + jieba 分词器实现，无需引入 ES。

## 五、文档解析与分块

| 工具 | License | 能力 | 角色 |
|---|---|---|---|
| **Docling**（IBM） | MIT | PDF/DOCX/PPTX/XLSX/HTML/图片 → 结构化文档；TableFormer 表格强；层级分块器 | **主力解析器** |
| Apache Tika | Apache-2.0 | 1000+ 格式纯文本抽取、MIME 侦测 | 兜底 + 格式探测 |
| PaddleOCR | Apache-2.0 | PP-OCRv5 中文 OCR、PP-StructureV3 版面/表格 | 中文扫描件兜底 |
| MinerU | v3.1 附加条款 | 中文复杂 PDF 极强（OmniDocBench ~95） | 备选（商用前法务审阅） |
| Marker / LlamaParse | GPL-3 / 商业 SaaS | — | 排除/云端备选 |

**分块策略结论**：结构感知分块（按标题层级/版面）+ 递归限长 + 父子分块（子块命中、父块返回上下文），chunk 记录 `(页码, bbox, 字符偏移)` 实现精确回溯。表格转 HTML/Markdown 保留结构后入块。

## 六、图片/视频处理基础设施

- **图片**：libvips（pyvips）生成缩略图——流式处理、自动 EXIF 转向，比 ImageMagick 快数倍、内存低一个量级；元数据用 exiftool 提取（EXIF/IPTC/XMP）。
- **视频**：ffmpeg + ffprobe（元数据/转码）+ PySceneDetect（BSD，场景检测）+ faster-whisper large-v3（转写，中文可考虑 SenseVoice/FunASR）。
- **VLM caption**：vLLM 部署 Qwen2.5-VL（Apache-2.0），仅对场景代表帧做 caption 控制成本——这是把"画面内容"变成可检索文本的关键一步，业界（Video-RAG 等）已验证该模块化范式。

## 七、对 LoomVec 的启示

| 能力 | 现有产品给我们的答案 |
|---|---|
| 资产管理 | 借鉴 Pimcore/Nuxeo：资产主表 + 可配置元数据 schema + 分类树/标签 + 版本 + 派生物表 |
| 语义单元与回溯 | 借鉴 RAGFlow/Dify：semantic_unit ↔ asset 外键关联 + source_locator（页码/坐标/时间戳） |
| 多模态检索 | 无现成产品，自建：图文统一嵌入（BGE-VL）+ caption/转写文本通道，双通道同库 |
| 企业集成 | 借鉴 Onyx/Dify：开放 REST API + API Key + Webhook；后续 MCP Server、数据源连接器 |
| 运营界面 | 现有产品普遍薄弱处：管线任务监控、失败重试、索引重建、模型切换是差异化机会 |
