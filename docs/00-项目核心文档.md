## 一、项目定位

LoomVec 是**企业级数字资产管理（DAM）+ 多模态语义检索平台**：用 DAM 的严谨体系管理资产（分类/标签/元数据/摘要/版本），用多模态向量让资产可被语义命中，且命中后能精确回溯到原文页码、图片区域、视频时间点。

三种使用形态：
1. **网页端**：企业最终用户创建与管理自己的知识空间（上传、标签/分类/元数据编辑、成员协作），并在空间内检索、浏览、问答；
2. **开放 API**：第三方应用集成——应用级走 API Key + Webhook + OpenAPI 契约，用户级走 OAuth 2.0 授权（代表用户调用）；
3. **运营台**：经营方治理平台：租户、用户、空间、配额、审核复核、管线与系统运营。

## 三、服务划分与职责边界

平台由六个组件构成，职责与边界如下（分层与部署形态详见 3.1）：

| 组件 | 仓库位置 | 运行形态 | 职责 | 明确不做 |
|---|---|---|---|---|
| 核心领域库 | `services/core` | 库（不可独立运行），被 api/worker 依赖 | 资产/空间/成员/语义单元/标签/元数据/配额的模型与逻辑、摄取管线定义、检索（dense+BM25+图谱三路混合召回+重排）、图谱（实体主表 + Apache AGE）读写、**资源级授权（空间成员关系、审核状态）**、对象存储适配、AI 网关客户端、扩展契约定义、数据库迁移 | 不处理 HTTP 协议、不管理 API Key/限流 |
| 管线执行器 | `services/worker` | Celery 独立进程（可水平扩容） | 执行管线任务：MinerU 解析调用、LLM 分片（chunk_markers）、嵌入、索引写入、图片缩略图/EXIF；进度事件上报；失败重试（实体关系抽取、两阶段实体合并、摘要/caption 随 P3 加入） | 不对外暴露任何接口 |
| API 服务 | `services/api` | FastAPI 进程（无状态，水平扩容） | REST `/api/v1/*`、认证（JWT/OIDC/OAuth 2.0/API Key）、**路由级授权与限流**、上传预签名签发、RAG 问答编排（检索→重排→LLM→带引用返回）、Webhook 投递、OpenAPI 契约产出 | 不直接写 SQL 绕过 core、不做管线逻辑 |
| 运维前端 | `apps/admin` | 静态 SPA | 租户管理、全量空间治理（含个人空间）、内容审核复核与下架、用户与角色、配额治理、API Key/OAuth 应用管理、管线监控与重试、模型与索引管理、审计与系统运营（模块与交互设计见 [04-运维前端设计.md](./04-运维前端设计.md)） | 不含业务 API 逻辑、不接管用户日常操作 |
| 用户前端 | `apps/web` | 静态 SPA | 知识空间管理（创建/成员邀请/角色）、资产上传与编辑（名称/标签/分类/元数据）、空间内检索浏览与问答（答案带引用与来源回溯定位）（模块与交互设计见 [05-用户前端设计.md](./05-用户前端设计.md)） | 不承担运营管理职能 |
| 扩展 | `extensions/` | 按 manifest 声明、由 core 契约加载 | 第三方插件（LLM/harness 类）、MCP 服务、AI 技能包 | 不修改平台核心代码 |

### 3.1 分层与部署形态

- **core 与 api 逻辑分离、物理同进程。** 二者在代码上边界严格（api 只经 core 的 service 接口操作领域）；api 进程与 worker 进程均以库形态依赖 core。满足任一条件时将 core 拆为独立服务：需要多语言/多协议消费、管线吞吐要求独立伸缩、多团队并行开发冲突。
- **权限模型分两层。** API 层负责认证与粗粒度授权（JWT / OAuth 2.0 令牌 / API Key 校验、路由 scopes、限流）；资源级授权（租户归属、空间成员关系 owner/editor/viewer、资产审核状态）由 core 执行，并作为过滤条件进入每次查询与向量检索——所有数据访问按**租户 × 空间 × 角色**三重过滤，防止越权检索。
- **请求处理与管线任务分离。** 同步请求（资产录入、检索、问答）由 api 进程处理；解析、分块、嵌入、索引等重异步任务由 worker 进程执行，两者通过任务队列解耦，worker 可独立水平扩容。

## 五、关键设计约定

1. **契约先行**：API 服务是 OpenAPI 契约的唯一产出方；`sdk-ts` 由契约生成，前端禁止手写接口类型。契约破坏性变更须升版本（`/api/v1` → `/api/v2`）。
2. **两层权限模型**（见 3.1 第 2 条）：路由 scopes（API 层）× 资源 ACL（core 层，进入检索过滤）。
3. **管线契约**：每个资产的摄取是任务 DAG，步骤幂等、带 `processing_job` 审计、发进度事件（`job.progress`/`asset.ready`/`asset.failed`），任何步骤失败可单独重试且不重做已完成步骤（以资产 checksum + 模型版本为缓存键）。
4. **检索契约**：dense + BM25 + 图谱三路召回（P2 起第三路为 clip_dense 以文搜图，图谱路 L3/L4 于 P3 落地），RRF 融合后**强制 cross-encoder 重排**；`Retriever` 接口隔离实现；结果统一为 `SemanticHit{unit_id, asset_id, unit_type, title, text, score, rank_scores, locator, highlight}`，locator 支持页码/区域/时间戳回溯（graph_evidence 实体关系证据链随 P3 加入）。
5. **模型无关**：core 的 `ai/` 网关统一 OpenAI 兼容协议；**向量化、rerank、VLM、LLM 直接使用云服务，平台不内置模型服务；供方地址、密钥、模型名均为部署配置，未来内网化时修改配置指向自托管端点即可**。
6. **配置分级**：`core/config.py` 默认值 + 环境变量 + `.env`；密钥不进仓库。
7. **检索质量护栏**：`evals/` 维护检索评测集与回归脚本；嵌入模型、分块策略、检索参数的任何变更必须通过评测回归，结果在运营端可视化。
8. **LLM 语义分片**：文档分片由 LLM 返回 `chunk_markers` 驱动，应用侧做确定性校验与尺寸钳制，失败兜底结构化分片（详见 [03-解析分片与图谱检索.md](./03-解析分片与图谱检索.md)）。

## 六、空间与权限模型

平台为**多租户架构**：tenant 是第一级隔离边界（数据、配额、认证域），space 隶属于租户。**Space（知识空间）是唯一的知识源层级**：一个 space 即一个完整知识源，内部不再分级；终端用户通过创建并切换 space 来切换知识源。空间的嵌入模型与分块预设从运营配置的白名单中选择，用户不可自定义分块参数。

### 6.1 空间类型与成员

| 类型 | 说明 |
|---|---|
| `personal` | 个人空间，创建者即 owner，仅本人可见 |
| `shared` | 共享空间，owner 可邀请成员协作 |

成员三角色：**owner**（空间设置、成员管理、**审核通过/驳回**、删除空间）、**editor**（上传资产、编辑/删除本人上传的资产、编辑标签/分类/元数据、查看待审队列）、**viewer**（检索、浏览、问答）。

### 6.2 可见性与审核

资产可见性 = 空间成员关系 × 审核状态。共享空间提供**"先审后见"开关**（空间级，默认关）：开启后新资产解析入库后进入待审状态——待审资产对 editor/owner 可见（标注待审、对 viewer 隐藏），**owner** 审核通过后才对 viewer 可见并参与全空间检索；驳回须填写理由并通知上传者（驳回即对 viewer 下架）；运营端始终可复核与下架任何空间的内容。

### 6.3 配额

维度为**存储量 + 文件数**，租户与空间两级配额独立校验（租户按各空间用量求和、空间按自身用量，0 = 不限）；闸门位于上传登记之前，超限拒绝并返回明确错误。**配额仅约束新增上传，不影响存量资产的检索与访问。**

### 6.4 上传链路

`POST /uploads` 签发对象存储预签名 URL → 客户端直传 RustFS（大文件 multipart）→ `POST /assets` 登记（MIME 嗅探、类型/大小白名单、配额校验）→ 触发摄取管线。大文件流量不经过 API 服务。

### 6.5 检索与问答作用域

检索与问答显式携带 `space_id`，或使用"我的全部空间"聚合模式；core 层执行成员校验，结果与引用只落在用户有权的空间内。

### 6.6 用户编辑边界

owner 可编辑/删除空间内任意资产；editor 可编辑/删除**本人上传**的资产（名称、标签、分类、元数据按空间元数据 schema）；API Key 登记的资产（无上传者）仅 owner 与同租户 API Key 可管理。

## 七、扩展体系

扩展不是松散堆放第三方代码，而是**实现平台契约的可加载单元**：

| 扩展类型 | 目录 | 契约要求 | 示例 |
|---|---|---|---|
| 插件（provider/harness 类） | `extensions/plugins/` | 实现 core 定义的 Protocol：`EmbeddingProvider` / `RerankerProvider` / `ParserPlugin` / `VLMProvider` / `LLMProvider` / `WebhookSink` | deepseek-harness 类 LLM 接入插件、新文档解析器 |
| MCP 服务 | `extensions/mcp/` | 对外暴露 LoomVec 能力为 MCP 工具（search/assets），走开放 API | `loomvec-mcp-server` |
| AI 技能包 | `extensions/skills/` | manifest（名称/描述/参数）+ prompt + 工具绑定 | "企业资料检索"技能供 AI 助手调用 |

加载机制：每个扩展带 `manifest.yaml`（类型、名称、版本、入口、配置 schema），core 的 `ext/registry` 按类型发现并注册；扩展只依赖 core 契约包，**禁止 import 平台内部实现**。优先以开放 API/MCP 消费平台能力，进程内 Protocol 插件仅用于 AI 供方与解析器这类必须贴近管线的场景。

## 八、数据与索引模型（概要）

详见 [02-技术方案.md](./02-技术方案.md) 第三节与 [03-解析分片与图谱检索.md](./03-解析分片与图谱检索.md)。要点：PostgreSQL 18 是唯一事实源（tenant / space / space_member / space_usage / asset / asset_version / asset_rendition / asset_tag / semantic_unit / tag / category / metadata / processing_job / user / user_role / role / api_key / notification / tenant_oidc_binding / system_config / oauth_client / oauth_authorization_code / oauth_access_token / webhook_subscription / webhook_delivery / audit_log；entity / merge_log 随 P3 创建）；知识图谱三层分工（P3 规划，当前未实现，AGE 镜像已就绪）——实体事实源为 PG 关系表，Apache AGE 同实例存图结构（节点/边带 chunk 溯源，**资产删除与图清理同事务级联**），Milvus `entities` 集合为可重建的链接向量索引；Milvus `semantic_units` 集合挂 `text_dense + sparse_bm25 + clip_dense` 三向量与标量过滤字段（id/space_id/tenant_id/asset_id/unit_type/model_version；标签/分类等业务过滤经 PG 侧收敛 asset_ids 后注入 expr；`space_id` Partition Key 为数据量增长后的优化项，P2 以标量 expr 过滤实现），`model_version` 支撑重嵌入过渡期过滤；派生物（缩略图/预览转码/关键帧）独立表存储于对象存储；**semantic_unit.locator 是"命中回溯来源"的保证**。

## 九、环境与部署形态

AI 供方（向量化、rerank、VLM、LLM）**直接使用云服务**，平台不内置模型服务；供方的服务地址、密钥、模型名均为部署配置。未来内网化时，将配置指向自托管端点（如 Infinity/vLLM）即可完成切换，不改代码。

| 环境 | 基础设施 | AI 供方 | 编排 |
|---|---|---|---|
| 开发/演示 | 本机 PG18（已装 18.6）+ Docker Compose 全套（Milvus Standalone/RustFS/Redis） | 云服务 | `deploy/compose` |
| 生产 | K8s：api/worker 多副本、Milvus 分布式、RustFS 集群 | 云服务；内网化后改配置切自托管端点 | `deploy/k8s` |

企业登录（SSO）以 **OIDC 对接企业 IdP**（如 Keycloak 或企业已有身份源）为优先路径；第三方的用户级授权走 OAuth 2.0 授权码流程。
