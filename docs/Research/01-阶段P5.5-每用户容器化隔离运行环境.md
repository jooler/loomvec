# 01-阶段P5.5：每用户容器化隔离运行环境（dsh 容器化研究）

> 状态：**研究定稿 v1.1（2026-09-19）**。本文是 [14-阶段P5](../14-阶段P5-dsh智能体对话与企业工作环境.md) §5.2「RuntimeProvider 隔离分级」中 **L2（容器化）的落地研究**，回答三个问题：① 用户对话时如何用上 dsh 全部能力（skills 等）；② 每用户服务端主目录 + 项目目录怎么建；③ 是否以及如何用 Docker 隔离每个用户，防止 dsh 访问其他用户或系统目录。
>
> 结论速览：**可行，且推荐立即排期**。推荐形态为「**每个工作环境（env）一个容器 = 一个 dsh runtime**」，**P5.5a 目标部署形态为宿主机网关**（现 dev.sh/deploy.sh 拓扑，事实 F15）+ `docker run -i` stdio 桥；RuntimeManager 的惰性 spawn / 复用 / 空闲回收逻辑**零改动**。三条关键设计原则：
>
> 1. **路径恒等原则**：容器内路径 = 宿主路径（唯一 bind mount 为 env 子目录自身）。这是 v1.1 相对 v1.0 最大的修正——v1.0 采用 `/home/agent/*` 美观路径并声称「patch 渲染不变」，经核实不成立：cordis.patch.yml 的会话根是宿主绝对路径（F13），会话 JSONL 按 `project_key(cwd)` 分桶且网关需按同一 cwd 重新计算定位（F14），路径翻译会同时破坏会话持久化与历史重放。路径恒等让 `envs.py` 渲染、`transcript.py` 解析**零改动**。
> 2. **MVP 统一 uid**：沙箱以网关进程的 uid/gid 运行，文件隔离靠子路径 bind mount；per-env uid 放到 P5.5b——因为网关必须直接读写同一棵 env 目录树（JSONL 解析、附件、workspace 浏览），per-env 属主与网关访问权冲突，需要共享组（setgid + default ACL）方案支撑（F16），不再作为 MVP 的「顺手可做」项。
> 3. **防火墙双链**：api/agent 在宿主机运行（F15），沙箱访问 api 走 host-gateway → 命中**宿主 INPUT 链**，DOCKER-USER（FORWARD 链）管不到——v1.0 只写 DOCKER-USER 是威胁模型盲区。v1.1 为 INPUT + FORWARD 两链分别下发白名单规则。
>
> dsh 自带沙箱（landlock）保留为进程内第二道边界；gVisor 因与 landlock 互斥排除（F8）。

## 1. 目标与问题定义

### 1.1 诉求

1. **能力完整**：web 端对话要能调用 deepseek-harness 的全部能力——skills（企业分发 + 项目级）、AGENTS.md 指令链、subagent、compaction、shell、文件编辑等（14 文档 §4.4 能力矩阵）。
2. **每用户主目录**：服务端为每个用户建一个「主目录」，用户可在其中创建自己的项目目录作为对话工作目录——类似在服务端给每个用户开了一个系统账户。
3. **硬隔离**：防止 dsh（以及用户项目里跑的任意代码，如 `pip install` 的包、`npm install` 的依赖）访问其他用户的数据或系统目录。

### 1.2 与现有 P5 实施的关系

- P0 已交付 `services/agent`（L1 `local` provider：网关进程直接 spawn dsh 子进程）。**问题**：所有用户共享网关的文件系统与网络命名空间，dsh 的 `workspace-write` 沙箱官方声明「不是安全边界」（landlock/Seatbelt 可被绕过的场景明确存在），不能作为多租户硬隔离。
- 本文不改 14 文档的任何既定协议（SSE 事件、会话模型、MCP 接入、审批矩阵、存储布局），只替换 RuntimeProvider 的实现级别。**P5.5a 目标部署形态 = 宿主机网关 + docker 沙箱容器**（与现 dev.sh/deploy.sh 拓扑一致，F15）；compose `app` profile 的容器化网关形态不在本阶段目标内（§6.6 说明取舍），K8s Pod 形态（14 文档 L2 的 k8s 版）沿用同一抽象，另行实施。

### 1.3 非目标

- 不在本阶段引入 K8s（当前部署形态是宿主服务 + docker compose 基础设施）。
- 不做知识库写回、不做 dsh 上游改造（`_launch_args` 属私有参数，按「版本锁定 + CI 协议冒烟」策略承接受更风险，见 §11）。

## 3. 威胁模型（容器要防什么）

被隔离对象不只是 dsh 二进制，而是「dsh + 用户项目内任意代码」（用户让 agent `npm install` 一个包并运行，等于运行任意不可信代码）。

| 风险 | L1 现状（同机子进程） | L2 容器化后 |
|------|----------------------|------------|
| 读其他用户 env 目录 | dsh 沙箱非安全边界，绕过即全读 | 每容器只挂载自己的 env 子目录（路径恒等）；**MVP 靠子路径挂载单边界，per-env uid 属主为 P5.5b 第二边界**（F16） |
| 逃逸到宿主机文件系统 | 同上 | 容器边界（runc + cap-drop ALL + no-new-privileges + 只读 rootfs）；内核漏洞逃逸成本高（可后选 Kata） |
| 内网横向（postgres/redis/keycloak/milvus、云 metadata） | 完全可达 | 专用网络 + DOCKER-USER 规则封 FORWARD 面；**INPUT 链规则收敛沙箱 → 宿主机自身可达面**（§6.5，仅放 api/MCP）；F12 的宿主端口回环绑定一并整改 |
| **宿主机服务面**（宿主上一切 0.0.0.0 监听的服务，F15 拓扑下沙箱经 host-gateway 可达） | 不适用（同机但同用户） | **INPUT 链白名单**：仅放 api 端口，其余 DROP（v1.0 盲区，v1.1 补齐） |
| 沙箱容器互访（跨用户） | 不适用 | 禁止沙箱子网内东西向流量（§6.5，依赖 `bridge-nf-call-iptables=1`，脚本自检） |
| 资源滥用（CPU/内存/磁盘/进程/fork 炸弹） | 仅靠网关池上限 | `--cpus/--memory/--pids-limit` + 磁盘水位 + 保留清理 |
| 模型被提示注入后执行破坏性 shell | 审批矩阵拒绝 + 沙箱（弱） | 审批矩阵保留 + **容器成为真边界**（最坏后果限于该 env 目录与容器资源） |
| 供应链（pip/npm 装包） | 直接污染宿主 | 污染限于容器内临时层；workspace 数据经挂载卷持久，镜像层随容器销毁丢弃 |

设计立场：**dsh 自带沙箱（landlock，进程内）+ 审批矩阵是「防线」；容器是「边界」**。边界必须独立于防线成立。

## 4. 隔离形态选型

| 方案 | 形态 | 结论 |
|------|------|------|
| A. L1 同机子进程（现状） | 网关进程内 spawn dsh | 仅 dev/单租户试点可用，不满足硬隔离 |
| **B. 每 env 一个容器，`docker run -i` stdio 桥（推荐）** | runtime spawn 时创建容器、terminate 时销毁；SDK `_launch_args` 指向 `docker run … dsh --profile sdk`；**P5.5a 目标形态 = 宿主机网关（F15）+ 本方案** | **采用**。F1/F10/F14 使 SDK、编排层、SSE 协议**零改动**；容器生命周期 = runtime 生命周期，F11 的回收/驱逐/串行全部白拿；不需要常驻空闲容器；宿主机网关使 docker daemon 访问面、bind mount、uid 分配全部天然成立（§6.6） |
| C. 常驻容器 + `docker exec` 桥 | 容器先起（守护进程或 sleep 入口），每次 runtime 经 exec 挂入 | 否。多一层容器/进程两级生命周期与孤儿状态；「容器即 runtime」的映射被打破；收益为零 |
| D. 容器内 HTTP/WS driver sidecar | 容器内跑一个小服务包装 Python SDK，网关走 HTTP/WS | k8s 阶段形态（14 文档 L2 的 sidecar 桥），compose 单机没必要多一跳；provider 接口已为它预留 |
| E. rootless Docker / Podman（rootless） | 同 B，但 daemon 本身非 root，uid 经 `/etc/subuid` 映射 | **作为 B 的部署变体保留**（宿主机不给 docker 组场景）；行为兼容 `docker run` CLI，代码经 `docker_host` 配置切换。**注意**：rootless 下 bind mount 的属主经 subuid 映射/squash，与 per-env uid 方案（P5.5b）冲突，二选一须在部署时验证（§11） |
| F. gVisor / Kata / Firecracker / E2B | 更强内核隔离 | gVisor 因 F8 **排除**（与 dsh 沙箱互斥）；Kata 是「完整 VM 内跑标准内核」，landlock 可用，作为高隔离租户后选项；microVM/E2B 仍是 14 文档 L3 |

选 B 的核心论证：dsh runtime 本来就是「一个进程 + 两棵目录树」（DSH_HOME、workspace），与容器是一一对应的自然映射；SDK 的 stdio 启动点（F1）恰好是唯一需要替换的东西，替换成本一个文件（`runtime/docker.py`）。宿主机网关（F15）让「网关进程 = 宿主用户」天然成立，从而 bind mount 无跨容器路径对齐、无 socket 挂载、uid/gid 直接复用进程身份。

┌──────────┐
│ apps/web │  （不变）
└────┬─────┘
┌────▼────────────────────────────────────────────────────┐
│ services/api（宿主机，不变：/agent/* facade、/mcp、鉴权）  │

│ loomvec-agent-env-{env_id}                                │
│  ├── dsh --profile sdk（原生 runtime，F3/F4）              │
│  ├── uid:gid = 网关进程 uid:gid（MVP 统一 uid，§6.1）       │

│  │     └── workspace/（initialize cwd）                    │
│  ├── cap-drop ALL · no-new-privileges · 只读 rootfs        │
│  ├── tmpfs /tmp 与 /home/agent（$HOME，§6.2）              │
│  └── 网络: agent-sandbox（专用 bridge，§6.5）               │
└───────────────────────────────────────────────────────────┘
  沙箱出网/出桥路径（两链白名单）：
  ├→ FORWARD 面（DOCKER-USER）：仅放 ESTABLISHED 与互联网出口；
  │   东西向（沙箱互访）DROP、RFC1918/metadata DROP
  └→ INPUT 面（宿主自身，F15）：仅放 api 端口（MCP），其余 DROP

## 6. 详细设计

### 6.1 用户主目录、项目目录与路径恒等原则（诉求 ② 的落地）

**env = 用户的服务端主目录**。一个用户默认持有一个 env（`agent_environment`），容器内布局 = 宿主目录树本身：

```
宿主机 = 容器内（路径恒等，唯一挂载点）
{storage}/envs/{env_id}/        ← docker run -v {env_dir}:{env_dir}:z（:z 仅 SELinux 重标，不改路径）
├── dsh-home/                   ← DSH_HOME（容器内与宿主同值）
│   ├── settings.yaml · cordis.patch.yml（F13：dsh 自动加载）
│   ├── AGENTS.md · skills/ · sessions/
└── workspace/                  ← initialize cwd（F9），主目录可见区
    ├── AGENTS.md
    ├── projects/               ← 用户的项目目录区
    │   ├── report-2026Q3/
    │   └── agent-demo/
    └── .loomvec/uploads/…（附件，不变）
```

**路径恒等原则是本方案的第一不变量**：容器内路径与宿主路径完全一致，因此——

- `cordis.patch.yml` 渲染的 `root:`（宿主绝对路径）在容器内同样有效（F13 不再是问题）；
- dsh 按 cwd 分桶写 JSONL 的位置 = 网关 `transcript.py` 按 `project_key(宿主 workspace)` 查找的位置（F14 不再是问题），历史重放、物理代次、消息聚合零改动；
- 附件 uploads、workspace 浏览、保留清理全部工作在同一路径语义上。

> **v1.0 的教训（保留作决策记录）**：v1.0 采用容器内 `/home/agent/{dsh-home,workspace}` 美观路径并声称「渲染逻辑不变」。经核实不成立：F13 会被容器内不存在的宿主路径破坏会话持久化（且 rootfs 只读时目录创建失败）；F14 会让网关按宿主路径算 `project_key` 而找不到容器内按 `/home/agent/workspace` 分桶的 JSONL，历史重放全断。若未来坚持美观路径，必须同步改造 `envs.py`（patch 渲染）与 `transcript.py`（分桶键）并全量回归——成本明确高于路径恒等的「模型可见路径前缀较长」这一外观代价。

- 用户（或代其操作的 agent）在 `workspace/projects/` 下自建项目目录；WorkspacePage 已可浏览/下载（14 文档 §9）。**v1 不为每个项目单独 spawn runtime**，理由是协议事实 F9：`cwd` 是 runtime 级，按项目拆分意味着容器数量随项目数膨胀，而收益（会话 JSONL 按项目分桶）可以用更便宜的方式获得——
  - **会话绑定项目**：`agent_session` 增加 `project_path`（workspace 相对路径，可空）。提问时网关在 contentBlocks 前注入一条 text 块：「本次会话工作目录为 `projects/<name>/`，交付物写入该目录」（注入点 `orchestrator._build_blocks`，与重放前缀、附件说明同一机制），并在 `workspace/AGENTS.md` 模板固化「项目目录规范」；
  - dsh 的文件编辑/shell 工具都在 runtime cwd 之下工作，相对路径自然落入项目目录；
  - **后续演进**：当出现「不同项目需要不同 AGENTS.md 指令链 / skills 隔离」的真实需求时，升级为 runtime 键 `{env_id}::{project}`（manager 注册表 key 与容器名各加一段），协议与存储零破坏——这是配置级改动，不是架构改动。
- **uid 策略（v1.1 修正）**：
  - **MVP：统一 uid**——沙箱以网关进程的 `{uid}:{gid}` 运行（`--user`）。宿主机网关（F15）下这就是部署用户身份，env 目录树属主即网关用户（`envs.py` 现有 0700 语义不变），网关读写与沙箱读写天然一致，**无需 chown、无需 uid 分配器**。文件隔离的单一边界是「子路径挂载」。
  - **P5.5b：per-env uid（第二边界）**——v1.0 曾把 per-env uid 列为 MVP 顺手项，经核实（F16）它与「网关直接读写同一棵树」冲突：env 树 chown 给 20001+ 属主后，非 root 网关反而读不了自己的 env。正确做法是**共享组方案**：env 树 `chown {env_uid}:{gateway_gid}` + 目录 `chmod 2770`（setgid 继承组）+ `setfacl -R -d -m g:{gateway_gid}:rwX`（default ACL 规避 umask 差异），容器 `--user {env_uid} --group-add {gateway_gid}`；`agent_environment.sandbox_uid` 列在 b 阶段随迁移加入。这样即使内核级逃逸，进程身份也只是低权 uid，不能直读其他 env（0700 + 不同属主）。

### 6.2 沙箱镜像：`loomvec/agent-sandbox`

- **依赖基底 = SDK + 自包含 runtime**（F4）。宿主机网关形态下网关镜像未必存在，沙箱镜像**独立构建**（构建上下文 = 仓库根，与 `services/agent/Dockerfile` 同法的 `uv sync --frozen` 装入 SDK + runtime wheel），叠加用户项目常用工具链：

```dockerfile
# deploy/compose/sandbox/Dockerfile（构建上下文 = 仓库根，独立于网关镜像）
FROM python:3.12-slim
ENV PYTHONUNBUFFERED=1 PIP_NO_CACHE_DIR=1
RUN apt-get update && apt-get install -y --no-install-recommends \
      git curl ca-certificates jq unzip less procps ripgrep \
    && rm -rf /var/lib/apt/lists/*
COPY --from=ghcr.io/astral-sh/uv:latest /uv /usr/local/bin/uv
WORKDIR /app
# 与 services/agent/Dockerfile 同法：先拷依赖清单（根 uv.lock + 各包 pyproject）
# 再 uv sync --frozen --no-dev，装入 deepseek-harness-sdk（含自包含 runtime，F3/F4）
# ……（依赖安装步骤同 services/agent/Dockerfile，此略）
# 入口即 dsh（argv 由网关注入 --profile sdk），无任何常驻守护。
# $HOME 由运行期 --tmpfs 提供（§6.3），镜像内不建 /home/agent。
ENTRYPOINT ["/app/.venv/bin/dsh"]
```

- 可选「重工具链」层（nodejs、build-essential、texlive 等）做成独立 tag（`agent-sandbox:devtools`），按租户/环境配置选择镜像（`agent.runtime.sandbox.image`）。**不把重工具链塞进默认镜像**：镜像体积、CVE 面与冷启动时间都随它增长。
- **镜像预构建是部署前置条件**：`deploy.sh` 负责构建（`docker build`/compose build）。镜像缺失时 `docker run` 会尝试去 Docker Hub 拉取不存在的仓库再失败，spawn 超时的报错具有误导性——deploy 后必须自检镜像存在（§9-11）。
- 技能依赖说明：skills 的执行 = dsh 工具（shell/编辑器）+ 镜像内工具链。企业 skills 若声明依赖（如需要 `python`、`git`），在镜像 tag 选择上覆盖；镜像是「能力声明」的物理载体，这也是企业级 skills 分发的自然锚点。

### 6.3 DockerSandboxProvider（新增 `runtime/docker.py`）

利用 F1/F10，替换启动 argv、其余 SDK 用法不变。**注意路径恒等：`cwd`、`runtime_cwd`、`DSH_HOME` 全部传宿主绝对路径**：

```python
class DockerSandboxProvider:
    async def spawn(self, cfg, env_id, token_env):
        DeepSeekHarness, DeepSeekHarnessConfig = _harness_cls()
        sb = cfg.agent.runtime.sandbox
        env_dir = cfg.env_dir(env_id)            # 宿主路径 == 容器内路径（§6.1 路径恒等）
        name = f"loomvec-agent-env-{env_id}"
        # 名字竞态兜底：池驱逐/复活窗口内同名容器可能尚未退出，
        # docker run --name 会直接失败；rm -f 幂等且阻塞到删除完成
        await _run("docker", "rm", "-f", name)   # 输出丢弃，容器不存在也算成功

        uid, gid = os.getuid(), os.getgid()      # MVP 统一 uid = 网关进程身份（§6.1）
        argv = (
            "docker", "run", "--rm", "-i",
            "--name", name,
            "--user", f"{uid}:{gid}",
            "--cpus", str(sb.cpus), "--memory", sb.memory,
            "--pids-limit", str(sb.pids_limit),
            "--ulimit", "nofile=1024:2048",
            "--security-opt", "no-new-privileges",
            "--cap-drop", "ALL",
            "--read-only",
            "--tmpfs", "/tmp:rw,noexec,nosuid,size=256m",
            "--tmpfs", f"/home/agent:rw,noexec,nosuid,size={sb.home_tmpfs}",  # $HOME 可写（工具缓存），随容器丢弃
            "-v", f"{env_dir}:{env_dir}:z",        # 唯一挂载：env 子目录自身，路径恒等；:z = SELinux 共享重标（非 SELinux 宿主无操作，不改路径）
            "--network", sb.network,               # agent-sandbox（§6.5）
            "--add-host", "host.docker.internal:host-gateway",    # MCP 等宿主目的地（§6.5）
            "-e", f"DSH_HOME={env_dir / 'dsh-home'}",
            "-e", "HOME=/home/agent",
            "-e", f"LOOMVEC_AGENT_TOKEN={token_env['LOOMVEC_AGENT_TOKEN']}",
            *(("-e", f"DEEPSEEK_BASE_URL={cfg.llm_base_url}") if cfg.llm_base_url else ()),
            *(("-e", f"DEEPSEEK_API_KEY={cfg.llm_api_key}") if cfg.llm_api_key else ()),
            sb.image,                              # loomvec/agent-sandbox:stable
            "--profile", cfg.agent.runtime.profile,  # patch 由 dsh 从 DSH_HOME 自动加载（F13）
        )
        harness = DeepSeekHarness(
            DeepSeekHarnessConfig(
                cwd=str(env_dir / "workspace"),    # initialize payload；容器内同路径（F9/F14）
                runtime_cwd=str(env_dir),          # docker CLI 的 Popen cwd（F10，宿主真实存在）
                env={**token_env},                 # 仅 docker CLI 进程环境（无害），容器内靠 -e
                dsh_home=str(env_dir / "dsh-home"),  # _launch_args 就位时 SDK 不消费（or 短路），
                                                   # 传真实路径仅为语义一致
                profile=cfg.agent.runtime.profile,
                provider=..., model=..., reasoning_effort=..., max_tokens=...,
                initialize_timeout_seconds=...,
                request_timeout_seconds=None,
                shutdown_timeout_seconds=5.0,
            ),
            _launch_args=argv,                     # F1：整体替换默认 argv
        )
        await asyncio.to_thread(harness.start)
        return harness

    async def terminate(self, handle):
        await asyncio.to_thread(handle.close)      # shutdown RPC → stdin EOF（F2）
        # F2 兜底：close 杀掉的只是 docker CLI；按名字强制清容器（幂等）
        await asyncio.create_subprocess_exec(
            "docker", "rm", "-f", f"loomvec-agent-env-{handle.env_id}",
            stdout=asyncio.subprocess.DEVNULL, stderr=asyncio.subprocess.DEVNULL)
```

要点与配套改动：

1. **stdio 桥的正确性**：`docker run -i`（无 `-t`）对多路复用的容器 stdout/stderr 做 demux，SDK 的 stdout JSON-RPC 读线程与 stderr 采集线程照常工作；JSON-RPC 按行分帧（`bufsize=1` 文本模式），容器不缓冲即可透传（Node 进程对管道 stdout 默认行写，实测确认即可，列入冒烟）。**stderr 噪声（已知且接受）**：docker CLI 自身的告警（如首次缺镜像的 pull 进度）会混入容器 stderr 进入 SDK 的诊断 deque——镜像预构建（§6.2）后此类噪声应消失，冒烟脚本断言 stderr 无 `Unable to find image`。
2. **terminate 兜底**（F2）：`shutdown` RPC 令 dsh 优雅退出 → 容器退出 → `--rm` 自动删除；`docker rm -f` 仅在 graceful 失败/超时后生效，按容器名幂等。
3. **孤儿容器 reconcile**：网关启动时 `docker ps --filter name=loomvec-agent-env-` 全量 `rm -f`（会话历史在宿主持久目录上，且路径恒等，resume 路径天然恢复，F14）。reaper 循环中同样定期对账（管理器注册表 vs 实际容器）。
4. **provider 选择**：`manager.py` 按 `agent.runtime.provider` 实例化 `local | docker`；`DockerSandboxProvider` 需要在 terminate 时拿到 `env_id`（给 handle 挂属性即可，SDK 句柄是普通对象）。
5. **健康探测**：spawn 后 SDK `initialize` 成功即视为健康（现状语义不变）；容器级异常（OOM、被杀）经 docker events 或 Popen 返回码归入现有 `runtime_restarted`/`error` 路径。
6. **失败 fail-closed**：docker daemon 不可达、镜像缺失、容器创建失败 → spawn 失败并向上返回明确错误码（`sandbox_unavailable`），**绝不回退到 L1 裸进程**。
7. **挂载执行位说明**：env 子目录 bind mount 不加 `noexec`（用户项目构建产物必须可执行，这正是沙箱存在的意义）；`/tmp` 与 `$HOME` tmpfs 的 `noexec` 是刻意的（不可信临时文件不得成为执行体）。

### 6.4 存储与文件归属

- **`storage_root` 保持宿主机目录**（宿主机网关形态下现状即成立，F15）：沙箱容器**子路径挂载**（只挂 `envs/{env_id}`，不是整个 envs 根）——挂整根会把所有用户的 env 一起暴露进每个沙箱，直接违背隔离目标；网关与沙箱共享同一棵宿主目录树（路径恒等）。
- env 目录权限沿用 0700，属主 = 网关运行用户（MVP 统一 uid）；per-env uid 属主 + 共享组为 P5.5b（§6.1、F16）。
- 目录树布局、AGENTS.md 渲染逻辑（`runtime/envs.py`）不变；**唯一渲染变更是 mcp url 按 provider 选择**（§6.5-3）。patch 的 `root:` 会话根因为是宿主绝对路径且路径恒等而**继续有效**（F13）——任何未来引入「容器内路径 ≠ 宿主路径」的改动都必须同时重审 `envs.py` 与 `transcript.py`（§6.1 决策记录）。
- **存量数据迁移**：`agent_envs` 命名卷中的既有 env 数据需一次性搬到宿主目录（`docker compose cp` / 直接拷 `_data/`），deploy 脚本提供迁移步骤与属主/权限校验；`LOOMVEC_AGENT_STORAGE_ROOT` 环境变量语义不变。
- 磁盘配额：MVP 用「`du` 计量指标 + 保留清理 + 水位告警」（复用 14 文档 §5.6 retention 任务）；文件系统级配额（XFS project quota / `--storage-opt size=`）列为 P5.5b 可选，因要求特定 fs 支撑，不作为 MVP 依赖。

### 6.5 网络隔离（v1.1 重写：FORWARD 与 INPUT 双链）

**拓扑事实（F15）**：api 跑在宿主机，不在 compose 里。沙箱访问 api 的路径是：容器 → `host.docker.internal`（= host-gateway，即网桥网关 IP）→ **宿主机 INPUT 链**。DOCKER-USER 挂在 FORWARD 链上，**管不到目的为宿主机自身的流量**——这是 v1.0 的威胁模型盲区：只写 DOCKER-USER 时，沙箱可以触达宿主机上一切 0.0.0.0 监听的服务。v1.1 双链下发：

**原则**：沙箱的网络目的地白名单只有三类——services/api（MCP，经 INPUT）、DNS 与模型 API 等互联网出口（经 FORWARD 默认放行）。

1. **专用 bridge 网络** `agent-sandbox`：固定 subnet（compose 显式声明，供防火墙脚本引用）；api/其他服务不加入该网络。
2. **防火墙脚本**（`deploy/compose/sandbox-firewall.sh`，deploy.sh 幂等下发；规则引用网段而非接口名，重启后由脚本重刷）：

```bash
# 前置自检：东西向 DROP 依赖 docker 对桥接流量过 iptables（其自身隔离规则同依赖）；
# 若宿主禁用了 bridge-nf-call-iptables，同网桥容器互访将绕过 FORWARD 规则 → 拒绝下发
[ "$(sysctl -n net.bridge.bridge-nf-call-iptables 2>/dev/null)" = "1" ] || {
  echo "FATAL: net.bridge.bridge-nf-call-iptables != 1"; exit 1; }

SANDBOX_NET=172.31.77.0/24        # agent-sandbox 固定子网（compose 显式 subnet，进 .env 可配）
API_PORT=38080                    # 宿主机上的 services/api（F15）

# ---- INPUT 链：沙箱 → 宿主机自身（FORWARD/DOCKER-USER 管不到的路径）----
# 幂等：先按注释标记清旧再下发。INPUT 规则必须 -I 1 插链首——宿主既有的宽泛
# ACCEPT（ufw/firewalld/手工放行）若排在前面，链尾 DROP 永远匹配不到。
# 每次插入都落到位置 1，故按逆序下发，最终链首次序：ESTABLISHED → api → DROP
iptables -I INPUT 1 -s $SANDBOX_NET -j DROP                              # 宿主其余端口全拒
iptables -I INPUT 1 -s $SANDBOX_NET -p tcp --dport $API_PORT -j ACCEPT   # MCP（api 需监听可达桥接来向）
iptables -I INPUT 1 -s $SANDBOX_NET -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT

# ---- FORWARD 链（DOCKER-USER）：沙箱 → 外部网络 ----
iptables -A DOCKER-USER -s $SANDBOX_NET -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
iptables -A DOCKER-USER -s $SANDBOX_NET -d $SANDBOX_NET   -j DROP   # 东西向 = 跨用户，全拒
iptables -A DOCKER-USER -s $SANDBOX_NET -d 169.254.169.254 -j DROP  # 云 metadata
iptables -A DOCKER-USER -s $SANDBOX_NET -d 10.0.0.0/8      -j DROP  # RFC1918 全拒
iptables -A DOCKER-USER -s $SANDBOX_NET -d 172.16.0.0/12   -j DROP
iptables -A DOCKER-USER -s $SANDBOX_NET -d 192.168.0.0/16  -j DROP
# 未匹配流量走 DOCKER-USER 默认 ACCEPT = 允许出网（模型 API/DNS）；域名白名单见 §6.5-5
# 注：双链仅覆盖 IPv4——agent-sandbox 网络默认无 IPv6 出口，云 metadata 的 IPv6
# 形态（fd00:ec2::254 等）不可达；若未来启用 IPv6 需同步补 ip6tables 白名单
```

   说明：① v1.0 的 `API_IP=$(docker inspect loomvec-api)` 删除——compose 中不存在该容器（F15）；若未来 api 容器化并接入专用网络，需在 FORWARD 面 RFC1918 DROP 之前补对应 ACCEPT。② 沙箱容器 cap-drop ALL 后无 raw socket，源 IP 伪造风险可忽略。③ RFC1918 DROP 的副作用：模型 API 若走内网代理（14 文档 §10 形态），需为该代理 IP 显式加 ACCEPT 前置；纯公网 API（deepseek.com）不受影响。
3. **mcp url 按 provider 渲染（新增 `agent.mcp.url_sandbox`）**：`envs.py` 渲染 patch 时，`provider == "docker"` 取 `url_sandbox`（形如 `http://host.docker.internal:38080/api/v1/mcp`），否则取 `url`（`http://127.0.0.1:38080/...`）。patch 恒重渲染（`envs.py` 现语义），切换 provider 无残留。**部署前置**：api 监听地址必须覆盖网桥来向（`0.0.0.0` 或至少 docker 子网），uvicorn 默认/现配的回环监听在 docker provider 下不可用——列入 deploy 自检。
4. **F12 整改**：compose 全部基础设施端口发布改为 `127.0.0.1:` 绑定，否则沙箱可经 host-gateway 直触达 postgres/redis/keycloak/milvus 的宿主发布口，绕过 INPUT 白名单（这些端口恰是 INPUT 上最危险的暴露面）。这一条无论是否做容器化都建议改。
5. **域名级出口管控**（可选，P5.5b）：模型 API 走互联网，iptables 管不了域名。需要时在 agent-sandbox 内放一个 forward proxy（squid/envoy，SNI 白名单），沙箱出网全部经代理。MVP 直接放行出网，理由：模型 API 必须可达，且容器内没有其他凭据可泄露（模型 key 经 `-e` 注入属预期持有者）。
6. **K8s 演进**：以上全部替换为 NetworkPolicy（default-deny + 白名单 egress）+ per-env PVC，即 14 文档 L2 的 k8s 形态；provider 接口不变。

### 6.6 Docker daemon 访问面治理（v1.1 修正：MVP 无 socket 暴露）

v1.0 假设网关容器化并直挂 `/var/run/docker.sock`，把「网关被 RCE = 宿主 docker root」列为 MVP 残余风险。目标形态改为宿主机网关（F15）后，**MVP 不存在 socket 挂载面**：网关作为宿主进程直接调用 docker CLI，其 daemon 访问面 = 部署用户的 docker 组身份。

| 层级 | 措施 | 阶段 |
|------|------|------|
| MVP | 宿主机网关 + 宿主 docker CLI；无 socket 跨进程暴露 | P5.5a |
| 加固（仅当网关未来容器化） | docker-socket-proxy：只放行 `containers/create,start,attach,wait,delete`、`images/json`、`networks` 等所需端点，DENY 一切其余（exec/Privileged 创建等）；网关经 `DOCKER_HOST=tcp://socket-proxy:2375` | 随容器化网关形态一并评估（P5.5b+） |
| 结构性 | rootless Docker / Podman rootless（daemon 无 root，`--userns=auto` 天然 uid 映射，注意 §4-E 的 bind mount 属主映射验证）；或上 K8s 后改为 namespaced ServiceAccount + RBAC（只能在该 namespace 建 Pod） | 部署形态升级时 |

残余风险（须在 README/安全清单声明）：**docker 组成员身份 ≈ root**（可经容器挂载根文件系统提权），网关被 RCE 等价于宿主失陷——这一点在容器化网关形态下同样成立（挂 socket 即此语义），并非宿主网关形态引入的退化。缓解事实：网关不暴露公网（内网 only，经 api facade），攻击面 = 内部 API + 依赖链；沙箱容器**不挂** socket、不在 docker 组，沙箱内逃逸不获得 daemon 访问权。

### 6.7 资源、性能与稳定性

- 资源上限逐容器强制（§6.3 argv）：CPU/内存/pids/文件句柄；OOM 时容器退出 → SDK run 异常 → 现有 `error(runtime_restarted)` 路径收尾，用户重试。
- 冷启动成本：容器 + dsh 启动 ≈ 1–3 s（原生 runtime 无 Node 冷启；前提是镜像已本地构建，§6.2）。MVP 不预热；`max_active_runtimes_per_node`（现值 20）即并发容器上限，池满驱逐逻辑不变。后续可做「spawn 后预 initialize」的温池。
- 空闲回收：manager 现有 reaper 直接生效——回收即 `terminate`，容器随之销毁，**无常驻空闲容器**（对比方案 C 的核心优势）。
- 镜像升级：`agent-sandbox` 双 tag（`stable` / `canary`），配置按 env 指定；升级 = 配置切 tag + 空闲回收自然轮替（profile patchReload=startup 语义一致，14 文档 §4.4）。
- 网关滚动重启：容器按名字可对账清理（§6.3-3）；in-flight 流以 `runtime_restarted` 收尾（现状语义）。

### 6.8 纵深防御总览

| 层 | 机制 | 挡什么 |
|----|------|--------|
| L0 | AGENTS.md 行为规范 + 审批矩阵（fail-closed） | 破坏性操作、越权检索意图（策略层） |
| L1 | dsh 原生沙箱（landlock `workspace-write`，容器内依赖 F6/F7 成立） | agent 误写 env 之外路径、误触自身 DSH_HOME（进程内） |
| L2 | **容器硬边界**（cap-drop ALL、no-new-privileges、只读 rootfs、子路径唯一挂载；per-env uid 属主为 P5.5b 第二边界） | 一切 L0/L1 失效后的实际损失范围 |
| L3 | 网络双链白名单（DOCKER-USER FORWARD 面 + INPUT 面，§6.5 / 未来 NetworkPolicy） | 横向移动、内网探测、宿主服务面、数据外带通道收窄 |
| L4 | 资源配额 + 水位告警 + 保留清理 | 资源滥用与磁盘耗尽 |

沙箱可用性自检：spawn 前 `landlock` 探测失败（F5 抛 `SandboxUnavailableError`）视为沙箱镜像/内核不满足 → 拒绝服务并告警，**不静默降级为 danger-full-access**（后者仅 dev profile 显式开启，14 文档 §5.5）。

## 9. 安全清单（对照威胁模型逐项验收）

| # | 检查项 | 验证方法 |
|---|--------|---------|
| 1 | 沙箱容器只挂自己的 `envs/{env_id}` 子目录，且容器内路径 = 宿主路径 | `docker inspect` Mounts 断言（冒烟脚本） |
| 2 | 跨用户不可达：容器 A 读不到容器 B 的目录/网络 | 双 env 集成测试：A 内 `curl` B 无路由；下发前 `bridge-nf-call-iptables=1` 自检通过 |
| 3 | 宿主面收敛：沙箱 → 宿主机仅 api 端口可达 | `iptables -C` 断言 INPUT 规则；沙箱内探测宿主其他 0.0.0.0 端口超时/拒绝 |
| 4 | 内网不可达：postgres/redis/keycloak/milvus/metadata 全拒 | 沙箱内逐一 `curl` 超时/拒绝（依赖 F12 整改 + RFC1918 DROP） |
| 5 | MCP 可达、模型 API 可达 | patch 渲染出 `url_sandbox` 的断言 + 正常对话 e2e |
| 6 | 非 root 语义（统一 uid）、无额外 capability、no-new-privileges、只读 rootfs | `docker inspect` 断言 + 容器内 `id`/写 `/usr` 失败 |
| 7 | 资源上限生效 | 容器内 fork 炸弹/内存吃满被杀，宿主不受影响 |
| 8 | landlock 工作在容器内（F5–F7） | agent 写 `workspace/` 外路径被拒（冒烟断言 `SandboxUnavailableError` 不出现） |
| 9 | spawn 失败 fail-closed（docker 不可用时不回退 L1） | 停 daemon/改 `docker_host` → 对话返回 `sandbox_unavailable` |
| 10 | 孤儿容器与名字竞态 | 杀网关 → 重启 → reconcile 后 `docker ps` 无残留；驱逐 + 复活快速循环下 spawn 不因重名失败（§6.3 pre-rm） |
| 11 | 镜像预构建：deploy 后镜像存在，首次 spawn 不触发 pull | `docker image inspect` + 冒烟 stderr 无 `Unable to find image` |
| 12 | 审计：容器创建/销毁/驱逐、防火墙脚本执行入 AuditLog/日志 | 日志抽查 |
| 13 | 凭据面：模型 key 只在容器 env（运行期），不落镜像/卷 | `docker history`、`docker inspect` 抽查 |
| 14 | F12 整改完成：基础设施端口 127.0.0.1 绑定 | `ss -tlnp` 断言 |

## 11. 风险与开放问题

| 风险/问题 | 等级 | 处置 |
|-----------|------|------|
| `_launch_args` 是 SDK 私有参数，上游可能变动 | 中 | 已按 14 文档供应链策略版本锁定（`0.1.5rc1`）+ CI 协议冒烟覆盖 spawn 路径；若上游移除，替代路径是方案 D（容器内 driver），provider 接口不变 |
| `docker run -i` 的 stdout 缓冲/分帧行为与直连管道存在差异 | 中 | 实施首日专项验证（长输出/二进制输出/高吞吐三个 case）；必要时 dsh 侧确认其行缓冲写管道的保证 |
| docker CLI 噪声混入 SDK stderr 诊断（pull 进度、告警） | 低 | 镜像预构建后消失；冒烟断言 stderr 无 `Unable to find image`；诊断 deque 仅为 tail 展示，不影响协议 |
| 同名容器竞态（驱逐/复活窗口内 `docker run --name` 失败） | 低 | spawn 前 `docker rm -f`（阻塞到删除完成，幂等）；安全清单 #10 覆盖 |
| landlock 依赖宿主内核 ≥ 5.13 + CONFIG_SECURITY_LANDLOCK | 低（现代发行版默认满足） | deploy.sh 增加内核能力预检（探测 `landlock_create_ruleset` 可用性），不满足时明确报错而非半途失败 |
| 同网桥东西向规则失效（宿主禁用 `bridge-nf-call-iptables`） | 低 | 防火墙脚本前置自检，不满足拒绝下发（§6.5-2） |
| gVisor 与 dsh 沙箱互斥（F8） | 低 | 现阶段不用 gVisor；gVisor 实现 Landlock ABI 后可作 `--runtime=runsc` 级升级（纯宿主侧变更） |
| 沙箱子网固定 IP 规划与现有网络冲突 | 低 | subnet 进 `.env` 可配；脚本启动时自检冲突 |
| DOCKER-USER / INPUT 规则漂移（其他组件改 iptables / 重启丢失） | 中 | 脚本幂等 + deploy.sh/定时任务重刷 + `iptables -C` 自检入监控 |
| per-env uid（P5.5b）耗尽 / 与宿主系统用户冲突 | 低 | uid_base 可配；网关在宿主运行 → 可查真实 `/etc/passwd` 去重（容器化网关时改为部署期校验）；共享组 ACL 方案需 ext4/XFS 支持 POSIX ACL（默认支持） |
| rootless docker 变体下 bind mount 属主经 subuid 映射/squash，与 per-env uid 方案冲突 | 低 | 方案 E 作为部署变体保留，启用前专项验证挂载属主行为（§4-E）；默认 MVP 不用 rootless |
| 模型 API 直连出网无法域名白名单 | 低 | P5.5b 出口代理可选；数据敏感租户可要求经内部 OpenAI 兼容代理（14 文档 §10 已有此形态；届时为代理 IP 加 RFC1918 前置 ACCEPT，§6.5-2 ③） |
| api 监听地址未覆盖网桥来向 → 沙箱 MCP 不可达 | 低 | deploy 自检（§6.5-3）；安全清单 #5 覆盖 |
| 模型 API key 经 `docker run -e` 注入，宿主上任何 docker 组成员可经 `docker inspect` 读到 | 中 | 可见面不扩大既有威胁边界（docker 组 ≈ root，§6.6，能 inspect 即能等价直读）；避免多管理主体共用宿主 daemon；P5.5b 评估 secret 文件挂载 + 轮换替代 `-e` |
| 防火墙双链仅覆盖 IPv4（云 metadata 的 IPv6 形态未拦） | 低 | agent-sandbox 网络默认无 IPv6 出口，IPv6 metadata 不可达；启用 IPv6 时同步补 ip6tables（§6.5-2 脚本内已注明） |
| SELinux 宿主（RHEL 系 enforcing）bind mount 无标签被拒 | 低 | env 挂载带 `:z` 共享重标（非 SELinux 宿主为无操作）；重标只改标签不改路径，路径恒等不受影响 |
