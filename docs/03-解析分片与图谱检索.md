> 状态：定稿 · 本文是 [00-项目核心文档](./00-项目核心文档.md) 的技术细节附件，覆盖文档解析、LLM 语义分片、知识图谱存储与混合召回。

## 一、文档解析：MinerU 内置自部署

| 项 | 决策 |
|---|---|
| 主解析器 | **MinerU 4.x，内置自部署**（`deploy/compose` 独立容器，`mineru-api` V1 HTTP 接口），worker 经 HTTP 调用 |
| 输入/输出 | PDF/DOCX/PPTX/XLSX/图片 → Markdown（标题层级）+ 表格 HTML + 版面块 JSON（type/text/page_idx/bbox，bbox 为归一化坐标）。入库解析（`MineruClient.parse`）提交 V1 `output_formats=["zip"]`，从产物包取 `markdown.md` 与 `structured_content.json`（拉平为版面块）：zip 内 Markdown 以 `images/page_{页}_{类型}_{序号}.jpg` 相对路径引用图片，图片文件不落库（前端 `MarkdownView` 渲染为占位徽标）。解析/上传文本落库与送 LLM 前统一经 `sanitize_text`（`core/pipeline/pages.py`）：去 C0 控制字符，并把内嵌图片 data URI（Markdown `![alt](data:image/…)` 与 HTML `src="data:image/…"`）替换为占位地址 `inline-image` |
| 调用约束 | 入库解析经 Redis 名额限流（`core/mineru_slots.py`）：同时在 MinerU 上解析的任务数 ≤ `mineru.max_concurrency`（默认 1）。容器版 MinerU 的 `MINERU_CONCURRENCY` 必须设为相同数值，二者共同决定实际并发数；`MINERU_INTRA_OP_NUM_THREADS` 是每个解析任务的 ONNX CPU 推理线程数，两个值应合并按实测 CPU 和内存余量调整，避免过度抢占。名额满时 `process_asset` 不占 worker 进程，延后 `mineru.busy_retry_seconds` 作为新任务重新入队（不记失败、不占 autoretry 次数，并恢复任务启动前的资产状态；因此迟到重试不会把已完成资产改回 processing）；名额为带 TTL 的租约（`timeout_seconds` + 900s），进程被杀到期释放。ParseStep 在下载原文件前先按 asset.mime_type 对 `MineruClient.likely_busy()` 做一次非原子探测，命中直接抛错——避免多进程抢满名额时每轮重试都重复下载原文件（真正占用判定仍在 slots.acquire()）。等待超时（`mineru.timeout_seconds`）、任务取消或进程被杀时 `DELETE /v1/parse/jobs/{id}` 取消 MinerU 任务。对外兼容层（docs/15）的任务不占名额 |
| 兜底 | Apache Tika 负责格式探测（MIME 嗅探）与不支持格式的纯文本抽取；中文扫描件由 MinerU 内置 OCR（PP-OCR 系）处理，复杂情况 PaddleOCR 兜底。**实施注记（P1）**：嗅探先以纯 Python 魔数校验实现（单点 `mime.py`），Tika 为后续替换项。**实施注记（2026-09-14）**：解析器接口已落地 `core/pipeline/parsers.py`——`Parser` Protocol + 链式注册（MinerU → 纯文本兜底），切换 Docling/PaddleOCR 仅需实现 Protocol 并在 `build_parser_chain` 登记 |
| 部署形态 | MinerU 4.x 以档位（tier）分级：flash/basic 为本地模型（CPU 可运行，自建 compose 部署固定 basic 档 + ONNX 小模型，首启自动下载权重）、standard/advanced 为 VLM 档（需 GPU/vllm 或远端 VLM，自建 CPU 部署不提供） |

## 二、LLM 语义分片与图谱合并抽取（chunk_markers）

**不使用固定长度/递归等传统分片**。MinerU 输出的 Markdown 具有稳定行号，分片边界由 LLM 决定、由应用确定性执行。分片与图谱实体/关系抽取设计为在**同一次 LLM 调用**中完成（见 3.2；**该合并抽取自 P3 起实现**，prompt 版本 chunk-graph-v5，管线五步 parse→chunk→graph→embed→index），本节先定义分片部分：

```
MinerU Markdown（行号稳定）
  → 长文按章节分批送 LLM（云端调用）
  → LLM 返回 chunk_markers JSON
  → 应用校验、钳制、切片
  → 语义单元（unit_type=text/table）入库
  （**P2 注记**：图片资产走独立分支——整图单单元（unit_type=image，caption+EXIF 文本），
   不做 LLM marker 分片；clip 图文向量见 02 文档 §三）
```

marker 契约：

```json
{"chunk_markers": [
  {"start_line": 12, "end_line": 47, "title": "Q3 营收分析", "keywords": ["营收", "季度对比"]}
]}
```

分批与请求上限：批次按章节边界切、每批正文 ≤ `pipeline.llm_batch_chars`（只在行间切）；提示词中单行超过 `llm_batch_chars` 时截断显示并注明原长（`chunking.numbered_lines`，行号不变，入库内容取原文）；各批 LLM 调用按 `pipeline.llm_concurrency`（默认 8，范围 1～32，1 = 串行；上限是每个资产各自的，多篇同时入库时总并发 = 篇数 × 该值，经 acp-gateway 时须小于网关的 `runtime.max_active_runtimes`，默认 32）并发，结果仍按批次顺序合并，分片、实体、关系的先后与串行时一致；某批失败只让该批走结构化兜底，不影响其它批；抽图谱时该批的实体关系同时缺失，批数记入 `version_meta.chunk.extraction_failed_batches`（§3.2）。供方有严格限流时调小。单资产写入图谱的实体 / 关系各有上限（`graph.max_entities_per_asset`，默认 300；`graph.max_relations_per_asset`，默认 600）。超限时**按重要性保留**，不按出现顺序截断：实体先看参与的关系数，再看被提及的次数，并列时靠前的优先；关系按被提及次数（权重）；被舍弃实体的关系随之丢弃；保留下来的仍按原顺序，未超限时与不设上限完全一致，超限时打 warning 日志 `graph_entity_cap_applied` / `graph_relation_cap_applied`。网关对单次 LLM 请求的提示词总字符设上限 `ai.llm.max_prompt_chars`（默认 100000），超限不发请求、抛 `ValidationError`，该批走结构化兜底。
LLM 供方可以是任意 OpenAI 兼容的 `/chat/completions` 端点（`ai.llm`）。JSON 输出模式默认随请求发 `response_format={"type":"json_object"}`；供方拒绝该字段时（如本机 acp-gateway 的 OpenAI 兼容接口，对它返回 400）把 `ai.llm.json_response_format` 设为 `false`，改靠提示词约束、宽容解析（含 ```json 围栏）和 `ai.llm.json_retries` 次重试取 JSON。用本机网关调用 Claude Haiku 5.5 的配置：`base_url=http://127.0.0.1:38095/v1`、`api_key` 取网关状态目录的 `local-api-key`、`model=agent:claude:haiku`、`json_response_format=false`；`temperature` / `max_tokens` 网关忽略。每次调用是一个独立的 Claude Code 会话；网关的兼容接口为 claude 建会话时关闭了内置工具（`tools: []`）。

应用侧确定性校验（不信任 LLM 的位置输出）：
1. 行号单调、落在文档范围内、区间不重叠（允许间隙，间隙内容并入前一 chunk）；
2. 尺寸钳制：过大的 chunk 按二级结构（标题/段落边界）二次切分，过小的与相邻合并；
3. 表格 HTML 块整体为独立语义单元，不参与 marker 切分；
4. 校验失败或 LLM 超时 → **兜底：按标题层级结构化分片**，记录 `chunk_method = structural_fallback` 供运营端审计；
5. 缓存键 = (asset checksum, 解析器版本, 模型, prompt 版本, 分片策略, 图谱抽取开关, 抽取领域配置 key + 内容指纹)（`core/pipeline/base.py` `chunk_cache_key`；领域配置只在 LLM 分片且抽图谱时计入）——重处理不重复计费，切换策略/开关/领域配置或改了自定义配置内容都能绕过旧缓存重跑；上次运行有批次抽取失败（`extraction_failed_batches` 大于 0）的结果不算可复用缓存，重跑会重新分片抽取；
6. 相邻同主题 chunk（title 前缀一致）构成父子关系：检索命中子块、返回上下文时合并父块。

### 2.1 分片策略、图谱抽取开关与抽取领域配置（可按空间或单次运行覆盖）

`ChunkStep` 每次运行先解析三个生效值，优先级 **本次运行覆盖 > 空间设置 > 全局配置**
（`core/pipeline/base.py` `resolve_chunk_strategy` / `resolve_graph_extraction` /
`resolve_extraction_profile`；白名单外 / 不可用的值按未设置处理，领域配置连全局值也不可用时落内置 `general` 并告警）：

| 维度 | 取值 | 全局配置 | 空间覆盖字段（白名单，留空=跟随全局） |
|---|---|---|---|
| 分片策略 | `llm`（默认）/ `structural` | `pipeline.chunk_strategy` | `Space.chunk_strategy`（`constants.CHUNK_STRATEGIES`） |
| 图谱抽取 | 开（默认）/ 关 | `graph.enabled` + `graph.extraction_enabled` | `Space.graph_extraction`（`on`/`off`，`constants.GRAPH_EXTRACTION_MODES`） |
| 抽取领域配置 | `general`（默认）/ `academic` / `biomedical` / `legal` / admin 自定义 key | `pipeline.extraction_profile` | `Space.extraction_profile`（见 §3.2.1） |

全局默认即 LLM 语义分片并同时抽实体关系；想让某空间零 token 成本入库，把该空间设为 `structural`（规则分片、不抽实体）。

- **单次运行覆盖（Finder「LLM重建」）**：`POST /api/v1/assets/{asset_id}/retry` 请求体
  （`RetryRequest`）可带 `chunk_strategy`（`llm`/`structural`）、`graph_extraction`
  （`on`/`off`）与 `extraction_profile`（可用的领域配置 key，否则 422），经 Celery 任务 `pipeline.process_asset` 的 kwargs →
  `PipelineRunner.run` → `ChunkStep.run` / `GraphStep.run` 透传，只作用于这一次运行，不写入
  资产或空间。覆盖只在从 `parse`/`chunk` 起跑时有意义，起跑步骤在 `chunk` 之后的请求返回
  校验错误。
  覆盖后的生效值进入缓存键：与上次处理不同则 chunk 步删除旧语义单元重新分片，后续
  graph/embed/index 随之重建（相同则命中缓存跳过分片）。Finder 右键「LLM重建」即以
  `step=parse, chunk_strategy=llm, graph_extraction=on` 调用该接口，完整重跑解析与后续步骤，
  使解析失败、尚无解析产物的资产也能重建（只对已就绪/失败的非图片
  资产显示）。图片/音视频资产不走本节分片逻辑：图片 chunk 步恒写 `skipped`；音视频分块由
  解析产物决定，chunk 步按全局 `graph.enabled` + `graph.extraction_enabled` 写
  `graph_status`，是否现场抽取实体由 graph 步按生效值复核决定（见下）。
- **`chunk_strategy=structural`**：整篇不调用 LLM，直接复用 `structural_fallback`（§本节
  "兜底"逻辑同款：按标题切节、表格整块不拆、超长按段落二次切、过短并相邻）作为**主路径**而非
  异常兜底；不产出实体关系，`asset.graph_status` 恒为 `skipped`，与图谱抽取开关互斥（选
  `structural` 即不看图谱抽取开关取值，不支持"规则分片+仍抽图谱"组合）。
- **`chunk_strategy=llm` 且图谱抽取关闭**：仍逐批调用 LLM 分片，但改用纯分片 prompt（无
  entities/relations 字段），比合并 prompt 输出小得多，真实控制是否向模型请求实体关系。
- `GraphStep` 遇到 `asset.graph_status` 为 `skipped` 时，按当前生效的
  `resolve_chunk_strategy`/`resolve_graph_extraction`（`core/pipeline/base.py`，与
  `ChunkStep` 共用，含本次运行覆盖——`PipelineRunner` 把同一组覆盖传给 chunk 与 graph
  两步）复核：仍该跳过才短路返回，不会因为"找不到抽取结果"误改判为
  `pending_retry`（图片资产走独立分支，同样受益于这条短路）；若空间配置已变更（如重新
  打开图谱抽取后单独重跑 `graph` 步），则不短路，继续走正常抽取逻辑。

## 三、知识图谱：PostgreSQL + Apache AGE

> 状态：**P3 已落地**（PG+AGE 镜像与冒烟脚本见 `deploy/compose/postgres-age` 与

> 合并/社区 `core/graph/merge.py`、`core/graph/communities.py`，L3 召回
> `core/retrieval/graph_retrieval.py`）。实施注记：图遍历（1~2 跳扩展、邻接补全、
> 社区检测）在 Python 侧基于 `load_space_edges()` 的边表执行——空间规模（万级边）内
> 往返成本可控且路径证据完整保留；Leiden 未安装 `loomvec-core[communities]` 时退化为
> networkx 贪心模块度；AGE 参数形参为 ag_catalog.agtype（非 jsonb）；全空间扫边
> （`load_space_edges` / `delete_asset_edges`）用有向匹配 `(a)-[r]->(b)`，每条边恰好返回一次、
> 走 `start_id` 索引——无向匹配会被 AGE 译成带 OR 的连接条件，退化为
> 「全图边 × 空间实体」嵌套循环；锚定单个节点的定点查询保持无向匹配。

**选型：Apache AGE（PostgreSQL 扩展，openCypher）**。理由：v1.7.0（2026-01）起支持 PostgreSQL 18 并成为主线版本；图谱与资产/语义单元**同库**——事务一致（删资产级联清理图数据）、备份恢复统一、运维零新增组件；Apache-2.0 无 license 风险。

### 3.1 图谱模型（按 space 隔离）

- 节点 `(:Entity {id, tenant_id, space_id, name, type, description, community_id})`
- 边 `[:REL {type, weight, chunk_ids[]}]`——`chunk_ids` 为溯源：命中边可反查语义单元；删除资产时按其清理边/节点
- 实体主数据：PG 关系表 `entity`（规范名/类型/描述/归属空间）为事实源，AGE 存图结构，Milvus `entities` 集合存链接用向量（可重建）

### 3.2 抽取与分片合并为单次 LLM 调用

长文按章节分批，**每个批次一次 LLM 调用同时返回两段结构**——分片 markers 与以行号锚定的实体/关系：

```json
{
  "chunk_markers": [{"start_line": 12, "end_line": 47, "title": "Q3 营收分析", "keywords": ["营收"]}],
  "entities":     [{"name": "A 公司", "type": "organization", "aliases": ["A"], "description": "…", "lines": [20, 44]},
                   {"name": "B 公司", "type": "organization", "aliases": [], "description": "…", "lines": [30, 35]}],
  "relations":    [{"head": "A 公司", "tail": "B 公司", "type": "PART_OF", "evidence_lines": [30, 35]}]
}
```

`type` 取值与关系推荐集合由抽取领域配置给出（§3.2.1，此处仅示意结构）；关系的 `head`/`tail` 必须是本次输出 `entities` 里的 `name`，否则该关系在解析后被丢弃（`sanitize_extraction`）。

- **收益**：全文只送一次，token 成本约为两次独立调用的一半；markers 与抽取共用同一行号坐标系——关系归属 chunk 由 `evidence_lines` 与 chunk 行区间**求交**（重叠最多者）确定，零额外对齐成本；
- **独立校验，互不牵连**：markers 按第二节的行号规则校验；entities/relations 按名称非空、type 合法、head/tail 可解析校验。任一部分失败不影响另一部分：
  - markers 有效、抽取无效（LLM 调用失败或实体/关系结构无效）→ 正常分片入库，该批没有实体关系产出；这类批数记入 `version_meta.chunk.extraction_failed_batches` 与 `version_meta.graph.extraction_failed_batches`，不改变 `graph_status`，也没有自动重试——`scripts/reextract_graph.py` 把失败批数大于 0 的资产视为未完成并重抽；
  - markers 失效、抽取有效 → 结构化兜底分片，抽取结果按兜底 chunk 的行区间照常归属；
  - `graph_status = pending_retry` 由 graph 步产生：写图异常，或资产没有抽取缓存（需从 chunk 步重跑）；两种都不阻断 embed/index，目前没有自动重试；
- 缓存键见第二节第 5 条（含抽取领域配置 key + 内容指纹）。

**抽取 prompt（chunk-graph-v5，`core/pipeline/extraction.py` `build_extraction_messages`）= 领域无关的底座 + 领域配置插槽**：

- 底座：分片契约（同第二节）；抽取目标是**跨文档知识图谱的「锚点实体」**——换一份相关文档也会独立提到、能在多份文档之间对上号的对象；每批实体数量预算 `entity_cap_for`（按本批可抽取字符约每 400 字 1 个，夹在 5~20）；只输出参与了至少一条关系的实体；全称作 `name`、缩写放 `aliases`；`name` 用原文规范写法、不带括号注释，`description` 一句中文 ≤40 字；只抽文中明确支持的关系；不抽本文自造术语、宽泛通用词、章节标题、图表编号、文档自身的页眉页脚/版权/出版信息；
- 插槽（来自领域配置）：类型清单及中文说明、优先抽什么、不要抽什么、推荐关系集合、要求不抽的关系（拦截集合）、命名额外规则、示例实体与关系、文档领域名。

#### 3.2.1 抽取领域配置（`core/graph/profiles.py` `ExtractionProfile`）

字段：`key`、`label`（中文名）、`description`、`entity_types`（[(小写 slug 类型, 中文说明)]，须含 `other`）、`priority_hint`、`exclude_hint`、`relation_types`、`blocked_relations`、`name_rules`、`example`（自洽示例：`{"entities": [{name, type, aliases, description}, …至少 2 个], "relation": {head, tail, type}}`，`head`/`tail` 必须是 `entities` 里的 `name`；渲染进 prompt 时每个实体附示意行号）、`skip_back_matter`（是否屏蔽论文后置章节）、`academic_noise`（是否启用论文元数据噪音词表）。`fingerprint` 为影响抽取的内容字段（除 key/description 外全部）的稳定哈希（sha256 前 16 位）。

| key | 用途 | 类型 | 推荐关系 | 拦截关系 | 后置章节屏蔽 / 论文噪音词表 |
|---|---|---|---|---|---|
| `general`（全局默认） | 通用文档 | person/organization/location/event/product/work（具名作品、文件、标准）/concept/method/dataset/other | PART_OF/IS_A/MEMBER_OF/LOCATED_IN/USES/CAUSES/CREATED_BY/OWNS/PARTICIPATED_IN/DERIVED_FROM/COMPARED_WITH/ASSOCIATED_WITH | 无 | 否 / 否 |
| `academic` | 任意学科学术论文（不抽作者、单位、基金、厂商） | general 去掉 work | USES/PART_OF/IS_A/CAUSES/ASSOCIATED_WITH/DERIVED_FROM/TRAINED_ON/EVALUATED_ON/COMPARED_WITH/OUTPERFORMS/LOCATED_IN | AFFILIATED_WITH/FUNDED_BY/PUBLISHED_IN/SPONSORED_BY/AUTHORED_BY/AUTHOR_OF/CITED_BY/CITES/EMPLOYED_BY/WORKS_AT | 是 / 是 |
| `biomedical` | 生物医药论文（在 academic 上叠加） | person/organization/product/location/event/concept/gene_protein/disease/cell_type/compound/method/dataset/other | academic 集合 + REGULATES/ACTIVATES/INHIBITS/INTERACTS_WITH/TARGETS/TREATS/EXPRESSED_IN | academic 集合 + SUPPLIED_BY/MANUFACTURED_BY/PROVIDED_BY/PRODUCED_BY | 是 / 是 |
| `legal` | 法律法规、裁判文书、合同（初版，建议领域专家审阅） | person/organization/statute/case/cause/contract/location/event/concept/other | CITES/APPLIES/INTERPRETS/AMENDS/REPEALS/SUPERSEDES/VIOLATES/PARTY_TO/PLAINTIFF_IN/DEFENDANT_IN/REPRESENTS/RULED_BY/APPEALS/CONTRACTS_WITH/EMPLOYED_BY/SUPPLIED_BY/OWNS/LIABLE_FOR/PART_OF/LOCATED_IN | 无 | 否 / 否 |

biomedical 另含：不抽 cells/patients/mice 类宽泛词、样本/患者/批次编号、数据库登录号、通用统计检验、抗体/试剂/耗材/质粒及货号、实验操作步骤；基因符号保持原文大小写；示例为 TGFB1 REGULATES EMT。general 示例为 ISO 9001 CREATED_BY ISO，academic 为 ResNet IS_A CNN，legal 为案号 APPLIES 民法典。legal 不抽审判长/审判员/法官/书记员等审判人员（含文末署名，person 类型不含法官）、送达落款套话等文书格式性内容，也不抽「原告」「被告」「本院」等泛称本身；法规用全称、条款写成「法规名+第X条」、案件优先用案号（案号自带的括号属名称本身，原样保留）；关系方向（`PLAINTIFF_IN`、`REPRESENTS`、`RULED_BY`、`APPEALS` 等的 head→tail）写在 `priority_hint` 中供模型遵循。

- **自定义配置**：存 system_config `pipeline.extraction_profiles`（admin 设置项，pipeline 组，值为 `{key: 配置 JSON}`，字段同上），写入前经 `parse_custom_profiles` 严格校验：key 为 2~32 位小写 slug 且不得与内置重名；最多 20 份；类型为小写 slug、不重复、须含 `other`；关系为大写下划线短语、推荐与拦截不得重叠；示例须自洽（2~4 个实体、name 不重复、关系的 head/tail 是示例实体且不相同、示例实体类型在类型清单内、示例关系类型在推荐集合内——因推荐与拦截互斥，也就不在拦截集合内）；各文本字段有长度上限；不认识的字段报错。
- **读取**：worker 每次 chunk 步（及媒体资产的 graph 步）经 `core/db/system_config.py` `load_extraction_profiles` 查一次（内置 + 自定义）；库里值不合法时告警并只用内置。空间引用的配置不可用（如自定义配置被删）时回落全局。
- **选择**：`Space.extraction_profile`（NULL = 跟随全局）；用户端/运营端空间创建与设置、管理端 `PUT /api/v1/admin/spaces/{id}/extraction-profile`（必填理由、写审计）均校验 key 存在（设置接口只校验与空间当前值不同的字段，值未变放行）。删除仍被空间或全局默认引用的自定义配置返回 422（信息列出引用的空间）；空间详情响应带 `extraction_profile_valid`，false 表示引用的配置已失效、管线正回落全局。`GET /api/v1/extraction-profiles` 返回可选配置（key/label/description/entity_types/is_builtin）与生效的全局默认 key，供三端下拉与实体类型中文标签使用。修改只影响之后新入库或重新处理的文件。
- **记录**：`version_meta.chunk` 与 `version_meta.graph`（pending 时）写 `extraction_profile` 与 `extraction_profile_fingerprint`（未抽图谱时为 null）。

#### 3.2.2 类型、后置章节与确定性兜底

1. **类型**：`ontology.canonical_type` 与领域无关，只做写法规范化（去空白、小写，非 `^[a-z][a-z0-9_]{0,31}$` 落 `other`），`entity_key` 用它计算；解析时（`parse_merged`）再按领域配置的类型白名单校验，不在清单内的落 `other`。
2. **后置章节屏蔽**（`core/pipeline/sections.py`，仅 `skip_back_matter` 开启时）：References / 致谢 / Funding / 作者贡献 / 作者信息与简介（Authors' information、About the authors、作者简介）/ 利益冲突与生成式 AI 使用声明（单独的 "Declarations" 标题不算）/ Ethics statement、Ethical approval 等伦理声明（单独的 "Ethics" 标题不算，伦理学论文的正文章节不能误屏蔽）/ 数据与代码可用性（含 "… statement"）/ Additional information / Supplementary 等标题下的行在 prompt 中以 `[略]` 占位——分片仍覆盖全部行号，但不在其上抽实体。标题可带数字编号前缀（`6 References`、`6.1 Data availability`、`6. References`）或罗马数字加标点（`VII. 致谢`）。
3. **确定性兜底**（`core/graph/entity_filter.py`，`parse_merged` 内执行）：
   - 通用层（所有配置，只收确定无误的拦截）：名称超长（>120 字符）、`et al` 引文式署名的 person、描述明确为「本文作者/通讯作者/致谢/作者单位/章节标题」或「本文参考文献条目」（描述以 本文/文末/文后/该文 加「参考文献」开头，或以「参考文献列表/条目」开头）的实体；描述里单独出现「参考文献」或「参考文献中」不算，如讲参考文献著录规则的标准《GB/T 7714-2015》照常保留；
   - 论文元数据层（`academic_noise`）：缩写署名的 person（`N.C.`、`JFK`、`Nielsen,M.`；法律文书里匿名当事人「A」是正规实体，所以不在通用层），以及描述含作者/员工/创始人/研究者/资助/供应商/厂商/制造商/被引/期刊等词的 person/organization 及文献、章节类实体；
   - 关系类型在配置 `blocked_relations` 内的直接丢弃；被丢弃实体的关联关系一并去掉。
   - 孤立实体：`graph.drop_isolated_entities`（默认开）时，汇总所有批次后丢弃不参与任何关系的实体（`sanitize_extraction`）；文本资产在 chunk 步、音视频资产在 graph 步现场抽取后都按此口径处理。

存量数据不会自动重抽（缓存键含 prompt 版本与领域配置，重新处理时才按当前配置重跑）。运维脚本：

- `scripts/reextract_graph.py`：分批重抽指定空间，**默认 dry-run**，`--apply` 才派发（走低优先级队列）。跳过「已完成」资产——status=ready，prompt 版本相同，领域配置 key 与指纹都等于该空间当前生效配置，非 mock、非规则分片，图谱未降级，且 `extraction_failed_batches` 为 0（旧记录无该字段时看 `fallback_batches`）。status 为 pending/processing 的在途资产与没有解析产物的资产不碰，只在输出里报数量，派发前还会再核一次状态。空间生效的分片策略为 `structural` 或图谱抽取关闭时整空间默认跳过，`--force-llm` 才强制。并发：`--inflight`（默认 2）同时在途的资产数，`--max-llm-calls`（默认 16）同时在途 LLM 调用数的硬上限，`--inflight × pipeline.llm_concurrency` 超过它拒绝运行。
- `scripts/gc_entities.py`：全部重抽完后清理陈旧实体，保留集 = AGE 里至少有一条边的节点；默认 dry-run，`--apply` 才删除 AGE 孤立节点、软删 PG 陈旧实体行并删除 Milvus 向量。
- `scripts/audit_entities.py`：按各空间（不含已删除空间）生效的配置只读审计存量实体与暂存关系的噪音。
- `scripts/pilot_extraction.py`：以当前 prompt 试抽若干篇文档并与库内旧抽取对比（`--profile` 可统一指定配置）。

### 3.3 两阶段实体合并

实体合并横跨资产边界，必须在空间级视角下处理，分两阶段：

**阶段一：管线内联链接（同步，随资产管线执行）**
1. 抽取实体规范化（大小写/全半角/别名表）→ 精确匹配实体主表；
2. 未命中 → 创建新实体（不做向量近邻链接）；
3. 本资产全部节点 upsert 与边写入在**单个 AGE 事务**内提交——原子生效或整体回滚，不留半图；
4. 边的 `chunk_ids` 追加关系归属的 chunk 溯源。

**阶段二：空间级异步合并（低优先级周期任务）**
1. 候选发现（`merge.name_candidates`）：同类型且 `variant_key` 相同的实体——规范名归一化之上，仅再容忍末尾小写复数 s，以及能由括号前各词首字母推出的括号缩写（如 `cancer stem cells (CSC)` / `cancer stem cell`；`T cells (CD4)` 与 `T cells (CD8)` 的键不同）。其余近似重复（向量近邻、编辑距离）不自动合并，目前没有按 winner/loser 手动指定合并的入口；
2. 合并动作：保留主实体规范名，合并 description、union 各边 `chunk_ids`、边端点重写；
3. **每次合并写 `merge_log`（PG 表）**，运营端可审阅与回滚；
4. 并发控制：per-space advisory lock，防止两个合并任务同时修改同一空间；
5. 触发：空间实体增量达阈值或定时，不影响资产管线时效。

### 3.4 数据主从与事务边界

| 存储 | 角色 | 一致性 |
|---|---|---|
| PG 关系表（`entity` 实体主表、`merge_log`） | **实体事实源** | 与资产同库同事务 |
| AGE（节点/边） | 图结构与检索遍历 | 每资产一个事务原子写入；**资产删除与图清理同库同事务级联** |
| Milvus `entities` | 实体链接向量索引 | 最终一致；对账任务可从实体主表全量重建 |

写入顺序：PG 实体主表 → AGE → Milvus 向量；每步幂等 upsert（确定性 ID = hash(space_id, canonical_name, type)），失败由管线重试。**资产删除时 PG（资产/语义单元）与 AGE（关联边/节点）在同一 PG 事务中级联清理**——这是图谱与事实源同库选型的直接收益。AGE 图与 Milvus entities 均可从事实源全量重建，运营端提供重建触发。

### 3.5 社区层（低优先级异步任务）

Leiden 社区检测（per space）→ LLM 生成社区摘要 → 摘要作为 `community_summary` 语义单元写入 Milvus，供全局总结类问题检索（见第四节 L4）。

## 四、混合召回（长期方案）

**三路并行召回 + 可选全局层，RRF 融合，强制 cross-encoder 重排**（当前已落地：L1 dense + L2 sparse + clip_dense 图文路 + RRF + rerank；L3/L4 与 graph_evidence 为 P3 规划）：

```
Query
 ├─ L1 dense      查询向量 → Milvus text_dense
 ├─ L2 sparse     BM25 → Milvus sparse_bm25
 ├─ L3 graph      实体链接（问题向量 → Milvus entities 取 `graph.link_top_k × 5` 个候选，IP 相似度 ≥ `graph.entity_link_threshold`（默认 0.65），再按「图中仍有该节点」过滤，取前 `link_top_k` 个）
 │                → AGE 1~2 跳邻居扩展 → edge.chunk_ids 回收语义单元（PG）
 ├─ L4 (可选)     community_summary 通道，服务"总结/对比"类全局问题
 ↓
RRF 融合去重 → 图谱邻接补全（命中 chunk 的 1 跳邻居 chunk 并入候选池）
 ↓
Cross-encoder 重排（Qwen3-Reranker，全部候选同池统一打分）
 ↓
Top-k SemanticHit（当前字段：unit_id / asset_id / unit_type / title / text / score / rank_scores / locator / highlight；graph_evidence 随 P3）
```

**为什么这是长期收益最大的组合**：
- 业界实践共识（GraphRAG / LightRAG / HybridRAG）：图谱与向量**互补而非替代**，混合召回稳定优于任何单路；LightRAG 的"实体层 + 主题层"双层检索是本设计 L3+L4 的模板；
- L1 覆盖语义相似，L2 覆盖精确词/型号/编号，L3 覆盖**多跳关系与跨文档实体聚合**（"A 公司母公司的法人是谁"类向量检索盲区），L4 覆盖全局归纳；
- 图谱成本发生在索引期（一次抽取），查询期遍历开销极小；`graph_evidence` 证据链让答案可解释，并为后续 Agent 式检索（沿图游走、多轮探索）预留能力；
- **重排强制启用**：三路召回的原始分数量纲不可比，cross-encoder 统一精排是质量收敛点；`evals/` 评测集按"语义相似 / 精确匹配 / 多跳关系 / 全局总结"四类维护回归。

**降级路径**：实体链接失败 → 自动退化为 L1+L2；新空间图谱未建 → 纯向量 + BM25。任何图谱故障不影响基础检索可用性。
